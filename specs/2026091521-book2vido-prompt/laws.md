### 本 spec 与铁律六的直接关系

铁律六里有一句自设的验收判据：

> **每个缓存产物都必须是「人工可改的口子」……新增任何缓存时必须同时回答「人改它生效吗」**

**提示词正是"人改它"最典型的对象，而本 spec 之前它的答案是「不生效」** ——
`script_key` 的因子是 `model / think / 句子数 / 章节文本`，**唯独漏了提示词**。
所以本 spec 不是"新增功能"，而是**补上铁律六自己开的验收缺口**。

## 〇之二、全局 specs 三条铁律

| # | 铁律 | 含义 |
|---|------|------|
| 1 | **No Spec, No Code** | 方案未文档化不写实现代码 |
| 2 | **Spec is Truth** | 文档与代码冲突，代码是 Bug，改代码 |
| 3 | **Reverse Sync** | 发现 Bug → 先补文档（根因/漏 AC/回归用例），再改代码 |

> 本 spec 的落地顺序即按此：先抓基线 → 写资产与加载器 → 逐字节校验 → 再接入缓存键。

## 一、Spec × Plan 双保障

- Spec = 静态真相源；Plan Mode = 动态执行上下文。
- 本 spec 需求不模糊（boss 原话已指明目标与理由），故**豁免追问**，代价与风险以对照表形式留给 boss 复核。

## 二、流程纪律

| # | 纪律 |
|---|------|
| 1 | AC 必须可测试（命令 / 单元 / 端到端），每条标验证方式 |
| 2 | 安全三条件（退出/幂等/回滚）——本项目无计费/库存/权限，但有**写操作（cache + 输出文件）**，故必填 |
| 3 | ✅ 三前置：复盘段非空 + 对账节非空 + 澄清状态已记 |
| 4 | execution-log 同步落账（append-only 事实源，禁事后回填） |
| 5 | 时间戳精确到分，用 `date` 获取，禁编时间 |
| 6 | 深度定档由 AI 建议、人确认（本 spec：standard，boss 2026-09-15 21:18 诉求即为授权） |

## 三、并行编排门禁

**本 spec 不开并行** —— 理由：

1. 改动集中在同一条窄链上（`promptlib` → `scriptwriter` → `cache` → `pipeline`），
   其中 `scriptwriter.py` / `cache.py` / `pipeline.py` / `config.py` / `config.yaml` 被多单元波及 → 按门禁 §3 一律划入串行。
2. 契约（`Prompt` 数据类 + 缓存键签名）是本 spec 的**唯一**冻结点，先冻后接，串行成本低于协调成本。
3. 无并行价值时写「**串行**」，不强制并行（门禁 §5）。

## 四、交互军规（boss 级，跨项目）

- 决策必须带专家意见（推荐哪个 + 为什么 + 代价 + 阶段适配），不骑墙、不给「都可以」。
- 中间产物必须落盘且可读可改（「人能接受微调」）—— 本 spec 把提示词也变成这种人可改的资产。
- 进度可见、失败不静默（军规 progress_visibility）。

## 五、质量门禁（置 ✅ 前）

```
□ 级联影响 — 调用链 3 跳已查（providers → scriptwriter → promptlib；pipeline → cache → models）
□ 测试 — 单元 + 05_validator 7 组 TC 通过 + validator-check 无占位符残留
□ execution-log — 与动作同步落账
□ ✅ 三前置 — 复盘 + AC 对账 + 澄清状态
```
