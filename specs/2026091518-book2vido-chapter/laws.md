## 〇之二、全局 specs 三条铁律

| # | 铁律 | 含义 |
|---|------|------|
| 1 | **No Spec, No Code** | 方案未文档化不写实现代码 |
| 2 | **Spec is Truth** | 文档与代码冲突，代码是 Bug，改代码 |
| 3 | **Reverse Sync** | 发现 Bug → 先补文档（根因/漏 AC/回归用例），再改代码 |

## 一、Spec × Plan 双保障

- Spec = 静态真相源；Plan Mode = 动态执行上下文。需求模糊先澄清（人审），定了才落 Spec。
- 执行中发现 Spec 遗漏 → 先改 Spec 再继续（铁律 3）。

## 二、流程纪律

| # | 纪律 |
|---|------|
| 1 | AC 必须可测试（命令 / 单元 / 端到端），每条标验证方式 |
| 2 | 安全三条件（退出/幂等/回滚）——本项目无计费/库存/权限，但有**写操作（cache + 输出文件）**，故必填 |
| 3 | ✅ 三前置：复盘段非空 + 对账节非空 + 澄清状态已记 |
| 4 | execution-log 同步落账（append-only 事实源，禁事后回填） |
| 5 | 时间戳精确到分，用 `date` 获取，禁编时间 |
| 6 | 深度定档由 AI 建议、人确认（本 spec：standard，boss 2026-09-15 18:47 授权推进） |

## 三、并行编排门禁（本 spec 触发并行，强制）

> 依据 `specs-engine references/orchestration.md`。AI 用「并行」包装一切会制造额外风险，故设硬门禁。

1. **契约未冻结不开并行**：`models.py` 必须先落盘并冻结签名。
2. **文件冲突验证**：各并行单元修改清单交集必须 = ∅（验证结果见 `01_analysis` §四-B）。
3. **共享文件串行**：`pipeline.py` / `__main__.py` / `config.py` / `config.yaml` / `scriptwriter.py`
   被多单元波及 → **一律划入串行收口**，不参与并行。
4. **并发上限 ≤ 4**（方法论建议 3–5；本 spec 恰 4 个无依赖单元，不盲目开满）。
5. **无并行价值时写「串行」**，不强制并行。

## 四、交互军规（boss 级，跨项目）

- 决策必须带专家意见（推荐哪个 + 为什么 + 代价 + 阶段适配），不骑墙、不给「都可以」。
- 中间产物必须落盘且可读可改（「人能接受微调」）。
- 进度可见、失败不静默（军规 progress_visibility）。

## 五、质量门禁（置 ✅ 前）

```
□ 铁律 Check — 三条铁律 + 项目宪法两条均无违反
□ 安全三条件 — 退出/幂等/回滚已明确（cache 与输出为写操作，必填）
□ 级联影响 — 调用链 3 跳已查（pipeline → 各模块 → CLI 入口）
□ 测试 — 单元 + 05_validator 8 组 TC 通过 + validator-check 无占位符残留
□ execution-log — 与动作同步落账
□ ✅ 三前置 — 复盘 + AC 对账 + 澄清状态
```
