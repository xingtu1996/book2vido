## 一、问题现状

**时间**：2026-09-15 18:47（boss 提出）。
**现象**：一本 348 页的 PDF，经流水线只产出一条 12 句、约 23 秒的视频，且内容只覆盖书开头的一小段。
目录、章节、页码结构全部丢失，无法「只要第 3 章」。

**影响范围**：
- 代码：`extractor.py`（抽取层）/ `scriptwriter.py`（取料层）/ `pipeline.py`（编排层）三个模块，共 5 处。
- 素材：`book2vido/关键对话.pdf`（348 页，实测）及后续所有长书。
- 用户可见行为：`run --input <书> --out <mp4>` 一条书 → 一条片，无粒度控制。

**时间线**：

## 二、根因分析

### 直接原因

| 证据 | 位置 | 说明 |
|---|---|---|
| `_pdf()` 把每页文本 join 成一个字符串 | `src/book2vido/extractor.py:14-16` | **页边界信息丢失**，无法再定位"第 3 章在第几页" |
| `body()` 用正则启发式猜正文起点 | `src/book2vido/extractor.py:25-40` | 靠猜，不是结构；失败退路是"跳过前 1/6" |
| `chunk = ...body(text)[:2500]` | `src/book2vido/scriptwriter.py:72` | 硬编码截断，348 页只用开头约 2500 字 |
| `run()` 单入口、无章参数 | `src/book2vido/pipeline.py:8` | 一次调用一条 mp4，无粒度选择 |

### 根本原因

**结构信息在入口就被主动丢弃**。`pypdf` 的 `PdfReader.outline` 能直接给出两级目录 + 精确页码
（实测 93 条），但 `_pdf()` 只调用 `page.extract_text()`，**把结构当噪声扔了**。

这不是"做不到"，是"没去读"——属于**设计缺陷**（入口设计时未把"结构"当一等公民），非边界或并发问题。

### ⚠️ 对底稿 `doc/10` 一处判断的更正（按铁律 3 Reverse Sync）

`doc/10` §4.1 表内断言：

> 新增 `models.py`｜现在 `Scene` 定义在 `scriptwriter` 里，却被 `visualizer`/`narrator` 导入 → **反向依赖**

**实测不成立。** 全仓 `*.py` 检索证据：

| 文件 | 是否 import `scriptwriter` | 判定 |
|---|---|---|
| `visualizer.py` | 否（只 import `pathlib` / `PIL` / `.icons`） | 无反向依赖 |
| `narrator.py` | 否（只 import `binpaths`） | 无反向依赖 |
| `tools/probe_perf.py:37` | 是（`from book2vido.scriptwriter import Scene`） | **测试脚本**，非生产依赖 |
| `icons.py:107` / `:259` | 否（注释中提及 `scriptwriter.Scene`） | 文档引用 |

**更正后的真实病根 = 契约所有权错位**（不是循环依赖，而是"契约被放在生成层"）：

1. **所有权错位**：`Scene` 是事实上的跨模块契约（生成 → 画面 → 配音 都按它对齐），
   却定义在 `scriptwriter.py:14-26`。契约应由依赖图的**塔尖**持有——谁定义契约，谁就成为解耦前提。
2. **裸 tuple 契约**：`compositor.compose(scenes_with_media: list[tuple])`（`compositor.py:8`）
   与 `pipeline.py:42` 的 `media.append((png, str(audio), dur))` 靠**位置约定**对齐；
   调换字段顺序**不会报错**，只会静默出错片——这是最贵的一类契约缺陷。
3. **无序列化契约**：`script.json`（人工微调口子）需要稳定 schema，当前只有内存 dataclass，
   没有 `to_json`/`from_json`，改完无法落盘回读。

> 结论：`models.py` 依然要建，但**理由是 1/2/3，不是"消除反向依赖"**。按铁律 3 回写 `doc/10`（见 `03_design` §八 清单）。

## 三、方案对比

| 方案 | 改动范围 | 风险 | 推荐 |
|------|---------|------|:----:|
| **A. 读 PDF outline 做索引 + 自建轻量分层**（4 新模块 + 5 处改） | 中 | 低（outline 缺失有降级链） | ✅ **采用** |
| B. 用 LLM 喂全文让它拆章 | 改 scriptwriter | **高**：4K ctx 装不下整书；会编造章名；慢 | ❌ 否决 |
| C. 引 LangChain / LlamaIndex 文本切分器 | 引重依赖 | 中：`RecursiveCharacterTextSplitter` 按**长度**切，不懂章节语义，解决不了本需求 | ❌ 否决 |
| D. 引 Celery / Prefect / Ray 做分布式调度 | 引分布式栈 | 高：给「12 句视频」上分布式调度是负收益 | ❌ 否决 |
| E. 保持现状（只取前 2500 字） | 零 | 需求不满足 | ❌ 否决 |

**性能/并发诉求的方案对比**（数据源 `doc/10` §二·探针 2/3/4，全部本机实测）：

| 诉求 | 直觉做法 | 实测结论 | 采用 |
|---|---|---|---|
| 并发调模型 | 线程池打 Ollama | 串行 2.2s vs 并发 2.1s（省 5%＝噪声），**服务端串行** | ❌ |
| 并发渲染 | 多进程画卡 | 12 张全量 **2.0s**（0.17s/张） | ❌ 不划算 |
| 并发 TTS | 线程池 | **28.9s → 2.2s（13.1x，12/12 成功）** | ✅ |
| 省 LLM 时间 | 上多线程 | 只有**缓存**（不重算）与**减调用**（批处理）两条路 | ✅ 缓存 |
| **热加载** | 监听文件自动重载 | **本项目无常驻进程**（CLI 一次性执行），无可热替换对象 | ❌ 不适用 |

> **「热加载」判定为不适用**：book2vido 是批处理 CLI，进程起→出片→退出。
> 真正对应「边点播边生成」的是 `run --chapter N`（按需生成）+ 缓存命中秒回——本 spec 两件都做。
> 若日后做网页点播（P5）才需要常驻服务，届时再评估热加载。

## 五、安全条件初判

| 条件 | 判断 |
|------|------|
| **退出条件**：什么时候停止？ | 缓存可用 `--no-cache` 整体关闭 → 行为退回当前语义；TTS 并发失败率升高时**自动降并发并最终退串行**；单章出片失败不阻塞其他章（记录并继续） |
| **幂等条件**：重复执行有什么后果？ | cache key = `sha256(文件字节) + 关键 config`；同 key 重跑**覆盖写**，不产生重复卡/音频；`cache/<book_hash>/ch<NN>/` 章间目录隔离，并发不同章无写冲突 |
| **回滚条件**：失败后如何恢复？ | 只**新增**模块 + 改调用点，**不删任何公开函数**；回滚 = 用 `.backups/2026091518-*/` 覆盖回 `src/`，旧 CLI 立即恢复 |

## 七、实现期发现（Phase 4~5，按铁律 3 Reverse Sync 回写）

> 这一节记录的**不是设计时的推演**，而是**动手实现/验收时才暴露**的缺陷。
> 三条都是"规格与实际不符"，且都是**验证动作本身**（而非编码）带来的收益。

| # | 缺陷 | 为什么设计时没看出来 | 更正 |
|:-:|---|---|---|
| 1 | **`video_key` 挂错键** → 手改 `script.json` 被静默丢弃 | 只看"键该含哪些因子"，没推演"用户在哪个文件上动手"。`script_key` 由**输入文本**推导，手改分镜不改它 → `hit_video` 命中**旧分镜渲染出的成片** | `video_key` 改挂 **sha256(分镜规范化 JSON)** 指纹 → 改一句只重渲染下游，LLM 不跑 |
| 2 | **命中路径白解析全书 11.9s** | 只算"成片要不要重做"，没算"命中时还顺手做了多少无用功"。`extract_pages` 5.9s + `outline.build` 6.0s = 每跑一次白干 | ①`outline.json` 优先 `load()` ②章切片落 `text.txt` ③`extractor.lazy_pages()` 延迟抽页 → 19.9s → **0.322s** |
| 3 | **`outline.json` 的"人工可改口子"是假的** | 与 #2 同源：每次重建，落盘的 `outline.json` 白存，手改不生效 —— 与 #1 是**同一类**"改了不生效"缺陷 | 与 #2 一并修：改成优先读缓存，手改即生效 |

**另一条"文档↔实现矛盾"（非 PDF 的正则兜底）**：

- `extractor.extract_pages` 文档称「MD/长文…分章走 outline 的正则/整本分支」，但正则段实际**不可达**
  （`_regex_flat` 只查每页首行，而 MD 被整篇当一页 → 最多命中 1 章 → 判失败）。
- 试把正则放开到扫全部行**也不该做**：MD 无页边界 → 所有章都落第 1 页 → `_to_chapters` 推出范围全是
  `p1-p1` → 切片**把整篇重复给每一章**，比 `whole-doc` 更糟。
- 处置：**保留**非 PDF → `whole-doc`（如实承认限制），改掉误导性文档，并在 `AC-3` 写明该语义。

> 🔑 **可复用教训**：本项目（乃至所有 AI 参与的流水线）的缺陷高发区**不在算法，而在
> "键/缓存/落盘文件"这类"看不见的契约"上**——它们不报错、只静默走错分支。
> 所以验证必须**逐条推演"用户改了 X 之后会发生什么"**，而不是只跑通 happy path。
