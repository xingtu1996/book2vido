## 三、运行时坐标（都在 Homebrew 前缀下，**默认不在非交互 shell 的 PATH 里**）

```bash
BREW=/opt/homebrew          # Apple Silicon 上的 Homebrew 前缀
ls $BREW/bin | grep -E "^(ollama|ffmpeg|ffprobe|rsvg-convert)"
```

| 工具 | 绝对路径 | 状态 |
|---|---|---|
| Ollama | `/opt/homebrew/bin/ollama` | ✅ v0.33.2，服务在跑 |
| FFmpeg | `/opt/homebrew/bin/ffmpeg` | ✅ 已装 |
| ffprobe | `/opt/homebrew/bin/ffprobe` | ✅ 已装 |
| rsvg-convert | `/opt/homebrew/bin/rsvg-convert` | ✅ 已装（librsvg，图标渲染用） |
| Python | `$HOME/.workbuddy/binaries/python/envs/default/bin/python` | ✅ managed venv |

### ⚠️ PATH 陷阱（本轮最重要的发现）

在**交互式终端**里 `ollama` / `ffmpeg` 能用（用户的 zsh 配置把它们带进了 PATH），
但在 **Agent 沙箱 / cron / 定时任务 / CI** 这类**非登录非交互 shell** 里，
`ollama` / `ffmpeg` / `rsvg-convert` **三个全部 `command not found`** —— 实测：

```bash
which ollama ffmpeg rsvg-convert     # 非交互 shell：全部 not found
```

**后果**：凡文档里写 `ollama pull xxx`、`ffmpeg -y ...` 的地方，
在自动化场景下都会静默失败或报 127。这不是本项目的问题，是 shell 启动方式的问题。

**三种兜底写法**（按推荐顺序）：

```bash
# ① 一次性补齐 PATH（推荐：写在脚本开头，不污染全局）
export PATH="/opt/homebrew/bin:$PATH"

# ② 直接用绝对路径（最稳，适合定时任务 / launchd）
/opt/homebrew/bin/ollama list
/opt/homebrew/bin/ffmpeg -version

# ③ 变量化（适合写进文档，读者自己适配 Intel Mac）
BREW=$(brew --prefix); $BREW/bin/ollama list
```

> 本项目提供了 `tests/verify_env.py` —— 它**不依赖 PATH**，主动按绝对路径找，
> 找不到就明确报「该装什么、在哪找」。跑它 = 环境体检。

## 四、本地模型清单（实际只有一个）

```bash
/opt/homebrew/bin/ollama list
curl -s http://localhost:11434/api/tags | head -c 400
```

| 模型 | 参数 | 体积 | 拉取时间 | 备注 |
|---|---|---|---|---|
| **qwen3:8b** | 8.2 B | **5.2 GB**（5,225,388,164 B ≈ 4.87 GiB） | 2026-09-15 | **唯一在用**，也是唯一已下载的 |

### ❗ 一个必须纠正的认知偏差

boss 印象中「本地已经有 **Llama**、**千问 3B** 或几 B 的模型」——**实测不成立**：

| 查过的地方 | 结论 |
|---|---|
| `ollama list` | 只有 `qwen3:8b` **一个** |
| `~/.ollama/models/manifests` | 只有 `library/qwen3` 一个家族目录 |
| `~/.cache/huggingface` | **不存在**（空，没拉过 HF 模型） |
| `~/.lmstudio` / `~/.cache/lm-studio` / `~/.llama` | **均不存在**（没装 LM Studio / llama.cpp） |
| `/Applications` | 无 Ollama.app / LM Studio.app（Ollama 走 brew 命令行版） |

**推论**：
1. 本机**没有降级备选模型** —— `qwen3:8b` 挂了/被删了，链路上没有第二个本地模型顶上，只会降级到 `rule`（规则截取，质量低但不中断）。
2. 所谓「Llama / Qwen-3B」多半来自 **Cherry Studio / 其他客户端里看到的云端或内置模型列表**，不是本机 Ollama 里的。
3. 想真有备选，得先 `ollama pull`。见下节可行性。

### 体积 4.9 vs 5.2：不是两个数，是两种单位

`du -sh ~/.ollama/models` 给 **4.9G**（GiB，二进制），`ollama list` 给 **5.2 GB**（十进制）。
同一个 5,225,388,164 字节。
**过去文档里两个数字并存过，看起来像漂移，其实是单位差** ——
写文档时统一注明单位，或干脆写字节数 + 复算命令。

## 五、加/换模型的可行性（16 GB 硬顶下算账）

| 候选 | 体积 | 本机评估 |
|---|---|---|
| `qwen3:8b`（现状） | 5.2 GB | ✅ 常驻约 5.9 GB，占 1/3 内存，跑批时别并行重负载 |
| `qwen3:14b` | ~9 GB | ⚠️ **会卡**。常驻逼近 10 GB，与 16 GB 总量 + 系统开销冲突 |
| `qwen3:1.7b` / `4b` | 1–3 GB | ✅ 可并存，适合做「速度对照 / 小模型兜底」 |
| Llama 系（如 `llama3.2:3b`） | ~2 GB | ✅ 可装。价值在于**换模型时验证提示词是否只适配 Qwen**（换模型 SOP 见 `models/README.md` §三） |

**建议的最小可行备选**：拉一个 `qwen3:4b`（约 2.6 GB）作为「快速档」，
与 `qwen3:8b` 并存也不到 8 GB，16 GB 机器扛得住。
这比直接上 14B 现实，且能给「8B vs 4B 质量差异」留下可复现对照。

换模型五步 SOP → [`models/README.md`](../models/README.md) §三（**不要在这里复制**）。

## 六、Python 与安装形态

| 项 | 实测 |
|---|---|
| 解释器 | `$HOME/.workbuddy/binaries/python/envs/default/bin/python`（managed venv） |
| 项目内 `.venv` | **不存在** |
| 安装方式 | editable（`src/book2vido.egg-info` 存在），故无需激活 venv 即可 `-m book2vido` |

> 与 `README.md` 快速开始里的 `python3 -m venv .venv` 是**两条路**：
> 开发机上走 managed venv（现状），分发形态走 `packaging/` 的 `.app`。
> 别混用 —— 在 managed venv 里再建 `.venv` 会得到两套 site-packages，出现「明明装了却 import 不到」。

### ⚠️ 实测：`-m book2vido` 直接跑会 `No module named book2vido`

editable 装的是**另一个解释器**，managed venv 里**没有**这个包。必须显式给源码路径：

```bash
export PYTHONPATH=src
$HOME/.workbuddy/binaries/python/envs/default/bin/python -m book2vido run --help
```

**完整可跑的一条命令**（三条坑一次补齐，实测 2026-09-19 出片成功）：

```bash
cd <仓库根>
export PYTHONPATH=src
export PATH="/opt/homebrew/bin:$PATH"
$HOME/.workbuddy/binaries/python/envs/default/bin/python \
  -m book2vido run --input samples/xxx.md --config config.yaml --out samples/xxx.mp4
```

漏 `--config` 不报错，而是**静默降级 `rule`**（分镜 0.02 秒出结果，质量烂）——
这是三个坑里最阴的一个（见 `models/README.md` §四）。
