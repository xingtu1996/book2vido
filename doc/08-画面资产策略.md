## 一、起因：一个被误会的资源

boss 在元宝收集到「**216 种手绘插画风格**」Skill（[原卡](https://yb.tencent.com/wx/ct/f/YFzntw1d6LC710)），
直觉是「拿它来给视频配插画」。

**它实际是什么**：`handraw-style` 是一个**文生图提示词库**——216 条「风格提示词」，
要**喂给图像生成模型**（SD / Midjourney / 即梦 / 混元等）才能出图。
它**不是现成图片素材**，本身不含任何图片。

**我们仓库里有什么**：只有元宝的**介绍摘要**，**没有那 216 条提示词本体**
（原文的「在线文档」链接没被捕获）。→ 目前**无法直接消费**。

**为什么现在不启用**：
| 路径 | 代价 | 结论 |
|---|---|---|
| 本地 SD（torch 已装，M1 Pro MPS） | 下 5–8GB 模型 + 磁盘已 92% + 单图 30–60s | ✖ 违反「极致省资源」 |
| 云端文生图 API | 有成本；且公司 key 禁用（合规红线） | ✖ |
| 人工批量生成一次 → 本地素材库复用 | 一次性人工，其后 ¥0 | △ 可选，但需先拿到提示词文档 |

> 结论：**216 风格列为「L3 后备弹药」，不是本周的画面解**。等前两级跑稳、
> 且 boss 拿到那份 216 提示词文档后，再以「一次性生成 → 永久复用」的方式接入。

### 补充（2026-09-15 21:43 boss 再次定调 —— 结论不变，理由升格为铁律）

对 L3 的直接影响：**不是"等文档到了就接"，而是"接之前重过三闸"**。

| 闸 | 216 风格的过闸情况 |
|:--:|---|
| ① 费用闸 | ✖ 要喂云端图像模型（有成本 + 公司 key 红线） |
| ② 体积闸 | ✖ 216 条提示词 → 可产出素材量级膨胀；本地出图 5–8GB + 30–60s/图 |
| ③ 替换闸 | ✖ 现役 L1（85 个 Tabler 图标 ≈1MB、¥0、命中率≈100%）已够用 |

**结论收紧**：从「L3 后备弹药，等文档」→ **「L2 已够用，不升级到 L3」**。
L3 只在一种情况下重启：**L1/L2 实测证明"画面读得懂"这个目标达不成**（判据见 §六 去重率 +
成片观感）。在那之前，画面层不再引入任何新依赖 —— 这正是"克制"的具体落法。

## 二、画面层三级策略

| 级别 | 手段 | 成本 | 依赖 | 状态 |
|---|---|---|---|---|
| **L1 关键词图标** | Iconify 开源图标（Tabler 线描）+ 行途蓝上色 | ¥0（一次性抓取缓存） | `rsvg-convert` 或 `cairosvg`（可缺省降级） | ✅ 已落地 |
| **L2 版式节奏** | 主视觉面板底色 + 序号 + 大标题 + 居中正文 + 品牌水印 | ¥0 | 无 | ✅ 已落地 |
| **L3 文生图插画** | 216 风格提示词库 → 本地素材库复用 | 一次性人工/算力，其后 ¥0 | 图像模型 / 216 提示词文档 | ⏳ 预留 |

设计要点：**L1/L2 全程离线优先**。图标命中缓存直接用；缓存缺失且无网时，
自动降级为「关键词首字大字」版式，**永不因缺图而中断出片**。

## 三、L1 为什么选 Iconify

- **量大**：聚合 200k+ 图标；**许可干净**（Tabler MIT / Phosphor MIT / Carbon Apache-2.0 / MDI Apache-2.0）
- **风格对**：线描单色，可 `?color=` 直接上**行途蓝 #056DE8**，
  与品牌军规「黑白极简 + 行途蓝、**不用 emoji**」完全一致（emoji 方案已被否）
- **极省**：单图标 SVG 几 KB，PNG 缓存 ~10–20KB；90 个图标合计 ~1MB 量级
- **可扩展**：`icons.py` 有两张中文词表 —— `KEYWORD_ICONS`（AI/工程化主题词）
  与 `CONCEPTS`（**叙事概念受控清单**，见 §六）；新增主题只需加一行

## 四、操作

```bash
# 预热图标缓存（联网一次，之后离线可用）
python -m book2vido fetch-icons

# 关闭图标层（回到纯文字版式）
# config.yaml → visual.icons: false
```

## 六、语义层补丁 · 受控概念清单（★ 2026-09-15 18:20，实图核对后补）

### 6.1 病灶：能出图 ≠ 出对图

第一版 `.app` 出片后，把《关键对话》PDF 的 12 张卡拼成总览逐个核对，发现：

| 卡片标题 | v1 实际图标 | 问题 |
|---|---|---|
| 定义 | 三角形 | 与文案无关联 |
| 技巧 | 九宫格点 | 像「应用启动器」，误导 |
| 心态 | 六边形 | 与文案无关联 |
| 情绪 | 六边形 | 无关联 |
| 表达 / 应用 / 改变 | **拼图 ×3** | **三张卡撞同一图** |
| 动机 / 案例 | **菱形 ×2** | 撞图 |

**12 张卡只出现了 6 个不同图形，语义相符不到 1/3。**

**根因不是「词表不够大」，是架构错位**：`KEYWORD_ICONS` 是按「AI / 工程化主题词」建的
（省 token / 缓存 / 管线 / 部署…），而 LLM 自由生成的 `keyword` 是**叙事型抽象概念**
（心态 / 观察 / 动机 / 案例）。两者交集极小 → `resolve()` 全部落空 →
走 `fallback_for()` 的 **crc32 散列**，从 16 个中性图形里取一个
（12 球进 16 箱，撞车是大概率事件）。

> 教训：**让 LLM 自由发挥、再事后翻译成结构化字段，永远会有漏网词。**
> 正确姿势是把**受控词表前置到 LLM 的输出约束里**。

### 6.2 药方：把图标语义前移到生成端

| # | 改动 | 文件 |
|---|---|---|
| 1 | 新增 `CONCEPTS`：**60 个叙事高频概念 → Iconify 图标**受控清单 | `icons.py` |
| 2 | 分镜 schema 从 2 字段扩到 3 字段，**清单直接注入 prompt**，要求 `concept` 必须从清单选 | `scriptwriter.py` |
| 3 | 取图顺序改为 `concept → keyword → 兜底` | `icons.py` |
| 4 | 兜底池 16 → 24，且**同一次运行内不重复**（`_used_fallback`） | `icons.py` |
| 5 | 版式：从「面板钉死 y + 正文在剩余空间居中」改为**「面板+间距+正文」整组垂直居中** | `visualizer.py` |

字段分工（关键设计）：

| 字段 | 归属 | 由谁决定 | 用途 |
|---|---|---|---|
| `text` | 口播文案（≤20 字） | LLM 自由生成 | 配音 + 卡片正文 |
| `keyword` | 画面大标题（2–4 字） | LLM 自由生成 | 卡片大标题，读起来自然 |
| `concept` | **图标语义标签** | **必须落在 `CONCEPTS` 清单内** | 决定用哪张图标 |

### 6.3 效果（同一 PDF、同一模型、同一参数，逐张实图核对）

| 指标 | v1 | v2 |
|---|---|---|

## 七、能不能让用户「一开始就选风格」？（★ 2026-09-15 22:50 boss 提议，评估结论：**不加代码**）

### 7.1 提议，以及一个需要先纠正的前提

boss 原话：「`assets/icons` 这个还挺有意思的……直接内载静态资源，根据**随机选用**
（如果可以，不是加东西啊，需要保持克制，综合看看这类东西）。但是既然是静态资源，
我们可以**开始就有个选择**啊，表情包或者啥的。」

**先纠正前提**：它不是「随机选用」，是**语义查表**。取图顺序是
`concept`（受控清单 85 词）→ `keyword`（工程词表 116 词）→ crc32 散列兜底（22 个中性几何）。
只有第三级才是"按词的散列取一个"，而且它是**稳定散列**——同一个词每次拿到同一张图，不是随机。

这个区别是硬需求：**可复现**。同一篇文章重跑，画面不能变，否则无法定位问题、无法做缓存、
无法对已发内容做广告回滚。「随机会好看一点」的代价是丢掉整条链路的可验证性。

### 7.2 实证：「换一套图」现在就能做到 —— 一行代码都不用写

boss 的判断（既然是静态资源，就能换）是对的，而且**机制一直在代码里**：
`config.yaml → visual.icon_dir` 可指向任意目录（`PillowProvider(icon_dir=...)`）。

实测：临时造了个 3 张图的替代包（其中一张染红，用来证明用的**确实是包里的图**）：

| 场景 | 结果 |
|---|---|
| concept 落在替代包内 | 输出卡里出现 **51357 个红色像素** → 确认图像源已切换 ✓ |
| concept 不在替代包内 | **正常出片**（降级为无图标版式），不中断 ✓ |

**所以：接口零成本，已经在。** 不需要加 CLI 参数、不需要加配置项、不需要加目录约定。

### 7.3 真正的成本不在「切换」，在「第二个包」

这是要拦一下的地方。切换免费，**第二套资源不免费**：

| 项 | 成本 |
|---|---|
| 换目录（用户自备 / `.app` 内置） | ¥0，已支持 |
| **重做映射表** | 换图标集＝图标名全变 → **116 条工程词表 + 85 条概念清单，201 条要重挂一遍** |
| 每加一套 | 上一条 × N，且每套都要重走一遍语义核对（§六 那轮 12 卡实图核对） |
| 体积 | 每套 ≈1.4 MB / 121 张，**且随 `.app` 分发**；三套就是 +2.8 MB |

> 一句话：**风格包的维护成本是「映射表 × 包数」的乘法，不是加法。**
> 而映射表恰好是本项目里最贵的那件资产——它是把 LLM 自由文本接到确定性画面上的那层胶水（§六）。
> **换皮便宜，重接神经贵。**

### 7.4 「表情包」这个方向，分两个场景看，结论相反

| 场景 | 判断 | 理由 |
|---|---|---|
| **「行途」自己的视频** | ✖ 负资产 | 品牌军规 P028 =「黑白极简 + 行途蓝、**无 emoji**」。表情包是彩色通用表情，与品牌语言正面冲突；同一条时间线上混排 = 账号没有主张 |
| **外部用户做自己的内容**（产品化后） | ✓ 正资产 | 他**不受**我们的品牌纪律约束。这时"能选"本身就是价值，哪怕选得不好看 |

**所以这不是"做不做"，是"给谁做"**：表情包属于**产品化阶段的功能**，
不属于**当前阶段的默认视觉**。现在装 = 增加分发体积 + 污染自家品牌一致性，
而收益为零（当前外部用户数 = 0）。

### 7.5 更省的替代：要「感觉不一样」，杠杆在版式不在图标

一个反直觉但可验证的判断：**同一份内容，观感差异的大头来自版式参数，不是图标**——
底色、字号梯度、留白、序号/品牌位、正文行距，全是**几十个数字**。
改一套主题的成本 ≈ 改 121 张图 + 201 条映射的 **1/100**，而且**纯参数、零新增资产**。

→ 若目标是"让用户可选风格"，顺序应该是：**先「配色 + 版式」主题，后「图标集」**。
三套配色（行途蓝 / 墨黑 / 赤陶）足以让同一篇文章看起来是三套片子。

### 7.6 结论与动作（本轮）

| 决策 | 内容 |
|---|---|
| **不做** | 不装第二个图标包 · 不做表情包 · **不加任何代码**（接口已在） |
| **做** | 本节留档（把「能做 / 成本多少 / 给谁做」写清楚）+ 进 `specs/` backlog |
| **重启条件** | ①出现外部用户且他明确问"能不能换图"；②行途需要品牌第二套视觉（如视频号竖版 / 小红书方版） |

> **留档一句话**：`icon_dir` 是口子，映射表是成本，品牌是底线。**口子已经开好了，别急着进货。**
