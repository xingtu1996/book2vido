确定性与模型的分工

一条流水线里，哪些环节该交给脚本，哪些才该交给模型——以及缓存为什么只是手段。 本页把这条判据写成可对照的尺子，并把实测发现的偏差逐条回挂证据。

  • 7 : 1脚本 : 模型（环境数）
  • 4 层缓存失效键
  • 5 条审计发现（2 条实测缺陷）
  • 2026-09-15审计日期

01判据：只看一件事——这一步有没有「歧义」

不是按「难不难」分，也不是按「贵不贵」分，而是按有没有唯一正确答案分。

有唯一答案 · 可验证 → 脚本

  • 结果能被断言（页码对得上就是对的）
  • 零 LLM、零幻觉、毫秒级
  • 错了能复现、能写测试
  • 成本 = 电费
歧 义 在 哪 一 侧

要理解语义 · 要做取舍 → 模型

  • 「哪句话最值得讲」没有标准答案
  • 允许不确定，但必须关进笼子
  • 输出受约束：只收 JSON、只能选给定清单
  • 成本 = 电费（本地模型）

一句话

模型负责「想出什么」，脚本负责「能不能过」。

02全链路分工：7 个环节，只有 1 个用模型

这正是「零 LLM、零幻觉、毫秒级」能成立的原因——它不是某个模块的自夸，而是整条链路的默认状态。

#环节手段用模型为什么
1抽文本 extractorpypdf✕PDF 解析是确定性的
2章节树 outline书内书签 → 正则 → 整篇兜底✕目录本来就印在书里，读它比猜它准
3取料切片 segmenter规则 + 算法版本号✕页码 → 文本范围是算术
4口播稿 / 分镜 scriptwriter本地 Ollama✓ 唯一「压成 12 句、每句配标签」是要判断的事
5信息卡画面 visualizerPillow 代码画✕版式固定，交给画图模型是浪费
6配音 narratoredge-tts / macOS say✕文字转语音不需要理解
7合成 compositorFFmpeg✕拼接是字节操作

模型的输出必须被「关进笼子」，分镜环节的约束是三层：concept 只能从固定清单里选（不许自造词）、只收 JSON 数组、句长 ≤20 字且句数 ≤12。模型一旦越界，脚本侧直接丢弃重试或降级到规则版。

算力还要花在刀刃上：think 必须显式传参——本机实测同一任务 think=true 36s / 568 tok，think=false 18s / 152 tok，但句子质量明显下降。所以「批量初筛关思考、定稿开思考」是个显式阀门，而不是靠模型模板的隐式默认（隐式默认会在换模型/版本时静默改行为）。

03缓存是手段：按「失效条件」分层，越贵越上游、键越窄

缓存不是为了「快」，是为了让最贵的那一步（LLM）不必重跑。所以键的设计原则是：只放真正影响该产物内容的因子。

层产物键含什么故意不含什么人改它生效吗
1outline.json书字节哈希—✓ 生效
2text.txt书哈希 + segmenter.VERSION + max_chars视觉 / 配音因子✓ 生效
3script.json书哈希 + model + think + 句数 + 章文本哈希配色 / 音色 / 尺寸✓ 生效
4ch<NN>.mp4分镜内容指纹 + 音色 + 配色 + 尺寸 + 图标号模型参数✓ 生效

两处设计值得单独点出，因为它们都是「踩过才知道」的：

  • 第 3 层故意不含配色/音色：否则用户改一句配色，就会把最贵的 LLM 产物一起废掉、白跑一遍模型。这就是「缓存是手段」的字面含义。
  • 第 4 层挂的是分镜「内容指纹」，不是输入键：早期版本挂输入键，导致手改 script.json 后分镜读到了新内容、成片却命中了旧渲染——用户的改动被静默丢弃。改挂指纹后：改一句 → 只重渲染下游，模型不跑。

纪律（写进铁律六）

新增任何缓存，必须同时回答「人改它生效吗」。答不上来的，就是白存的死文件——落盘了、但没人能改、也没人会用。

04实测证据：缓存到底有没有在工作

同一份素材（102 字 md），两条路径各跑两遍。--fast 关闭思考模式以压缩耗时。

run --chapter 首次

53.5 s

缓存: miss · 12 句

run --chapter 第二次

0.0 s

缓存: hit · 跳过模型省 ~36s

batch 第二次

重跑

输出与第一次逐字相同

# A. run --chapter 1（新链路，缓存生效）
$ book2vido run --input tiny.md --chapter 1 --out a.mp4 --fast
    · 分镜：102 字 → 本地模型（think=False）…
    · 画面：渲染 12 张卡…
    · 配音：12 句并发（workers=12）…
    · 合成：FFmpeg concat…
耗时      : 53.5 s       缓存      : miss

$ book2vido run --input tiny.md --chapter 1 --out a2.mp4 --fast
    · 分镜：缓存命中 12 句（跳过模型，省 ~36s）
    · 成片：缓存命中 → a2.mp4
耗时      : 0.0 s        缓存      : hit

# B. batch（同一素材，第 1 次与第 2 次输出完全一致）
$ book2vido batch --batch ./src_in --out out --fast      # 第 1 次
    · 分镜：85 字 → 本地模型（think=False）…
$ book2vido batch --batch ./src_in --out out --fast      # 第 2 次
    · 分镜：85 字 → 本地模型（think=False）…   ← 又跑了一遍模型
{"scenes": 2, "seconds": 19.2, "cost": 0.0001, "cache": "miss"}

缓存目录里确实躺着齐全的中间产物（12 张卡 + 12 段语音 + 12 个 clip）——它们被落盘了，但下面第 2 条发现会说明，落盘不等于被复用。

05审计发现（按处置优先级分档）

A 级 建议开 spec 修 · B 级 建议补文档 · C 级 记录待议

A 级F1 · batch 完全不走缓存，且状态显示为「miss」而非「关闭」
证据
实测：同一素材连跑两次，两次都打印「分镜：85 字 → 本地模型」，逐字相同；输出 JSON 为 {"scenes": 2, "seconds": 19.2, "cost": 0.0001, "cache": "miss"}。
代码：__main__.py:93-100 的 _batch() 调用 pipeline.run()，而 pipeline.py:192 显式 Cache(..., enabled=False)。
根因
batch 复用 T2V-001 兼容入口。该入口刻意关闭缓存（为保持旧副作用面），T2V-002 引入的按章 + 缓存能力没升到 batch。
后果
  • 最贵的环节（LLM）在最需要缓存的场景——批量初筛——每次重跑
  • 状态标签说谎：pipeline.py:88 在「缓存被关闭」时也返回 "miss"，用户无法区分「查了没命中」与「根本没启用」
  • batch 还不读目录、整本当一章，与 run 的能力代差会持续扩大
修法
_batch() 改走 run_book()（按章 + 缓存），或给 pipeline.run() 加 enabled/cache 参数；同时把缓存状态拆成 hit / miss / off 三态。
复发判据
任何新入口都必须回答「它走缓存吗」；成本日志里一个标签不允许同时表示两种含义。
A 级F2 · 中间产物已落盘，却没有被当缓存复用
证据
缓存目录实测含 card_001.png … card_012.png、voice_1.mp3 … voice_12.mp3、clip_000.mp4 …；
但 pipeline.py:68-80 在每次「成片未命中」时无条件全量重渲染卡片与重跑配音——visualizer.py:79 的 card() 与 narrator.py:29 的 speak_many() 都没有「已存在即跳过」的判断。
根因
缓存边界划在「分镜」和「成片」两层，中间产物只是工作文件，没有命中条件。修一句分镜 → 整批下游重算。
后果
  • 速度：手改一句 → 12 张卡重渲染 + 12 句重配音 + 12 个 clip 重编码（「人改一句、十几秒看到新片」里的十几秒就是这个）
  • 更重要的非速度后果：TTS 走 edge-tts 需要联网；断网时会回退本地 say，音色整片变掉。若按句缓存 mp3，改一句时其余 11 句仍能保住原云音色
修法
给 card / voice / clip 各挂内容指纹（scene 文本 + 版式因子）做命中跳过；与现有 video_key 同一套思路，只是粒度下沉一层。
复发判据
落盘 ≠ 缓存。写任何新中间产物时，同时写清「命中条件是什么」——没有命中条件的产物，只是垃圾。
B 级F3 · 「零 LLM、零幻觉、毫秒级」原本只是模块自述，不是全项目判据
证据
该表述原仅见于 outline.py:1 的模块 docstring 与 doc/10-目录索引与按需生成.md:36，是「目录索引这个模块的特性」，未进入 CONSTITUTION.md。
后果
后人往链路里加环节时没有可对照的尺子——「加个模型让它更聪明」是最自然的直觉，缺少一条成文铁律去挡住它。batch 与 run 的能力分叉（F1）就是缺尺子的实例。
修法
已修：CONSTITUTION.md 新增铁律六 · 能用脚本就别用模型（确定性优先），含分工判据、7:1 分工表、「关进笼子」约束、缓存分层纪律、以及「新增缓存必须回答人改它生效吗」。
复发判据
任何新增环节在 spec 里必须标注它落在「脚本侧」还是「模型侧」及理由。
C 级F4 · FFmpeg 详细日志未静音，淹没成本日志
证据
compositor.py:30-38 与 :46-49 调用 ffmpeg 时未传 -v error；实测一次 batch 运行刷出上百行 banner 与逐帧进度，把面向人的成本日志挤出视野。
后果
CLI 可读性下降；对「无人值守批量跑」场景尤其糟——真正的错误信息会被噪音埋掉。
修法
合成调用加 -v error（与本项目其它环节一致），失败时再回吐 stderr。
复发判据
面向人的 CLI 输出里，不该出现第三方工具的 banner。
C 级F5 · visual.w/h 只在卡片渲染生效，合成阶段硬编码 1080×1920
证据
providers.py:35 把 cfg["visual"] 整体传给 Pillow（w/h 生效于卡片）；而 compositor.py:33 写死 scale=1080:1920 … pad=1080:1920；同时 cache.py:70 的 video_key 包含 w/h。
后果
把尺寸改成 720×1280 想省资源 → 卡片按 720 画、合成又放大回 1080×1920，等于白改（还多一次缩放损失）。缓存会正确失效，所以不会出错，只是「改了没有预期效果」。
修法
合成阶段改为读同一份 cfg["visual"]["w"]/["h"]，去掉硬编码。
复发判据
同一个配置项出现在两处、其中一处是字面量 —— 必查哪一处是死代码。

06建议与待拍板

项建议性质
F1 batch 无缓存开 T2V-005 spec 收口（含缓存状态三态化）行为变更，需 boss 定优先级
F2 中间产物未复用与 F1 同一 spec 内一并做，粒度下沉一层行为变更（改后「人改一句」会更快、音色更稳）
F3 原则成文已完成（铁律六）规则类，已直接入库并回写 CHANGELOG
F4 / F5各一行改动，可随时顺手带上修补类，不阻塞

写在最后

这条原则真正的价值不在「省了多少秒」，而在把不确定性收敛到一个点上。整条链路里只有一个环节可能给出无法复现的结果——只要把它圈出来、给它约束、给它缓存，剩下的一切就是可解释、可测试、可重跑的。
缓存是这个收敛动作的工具：让模型回到它唯一该干的事。
