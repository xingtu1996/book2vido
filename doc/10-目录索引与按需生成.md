# 10 · 目录索引与按需生成（含性能实测）

> 更新：2026-09-15 19:10 ｜ 状态：**P1–P4 已实现并验通**（见 `specs/2026091518-book2vido-chapter/`）
> 本文所有数字均为本机实测（M1 Pro 16GB / qwen3:8b / 348 页《关键对话》），命令见文末。
>
> ⚠️ **本文是"设计底稿"，实施后有三处口径被实测更正**（细节见 spec 的 `01_analysis` §七）：
> ① `video_key` 改挂**分镜内容指纹**（原挂 script_key → 手改分镜会被静默丢弃）；
> ② 命中路径**不得重复解析全书**（原每次跑都抽 348 页 + 重建大纲 = 白干 11.9s，全命中 19.9s → 0.322s）；
> ③ 非 PDF（MD/长文）**一律 `whole-doc`**，不走正则分章（无页边界，硬分会让每章切片到整篇）。

## 一、要解决的问题

现状 `pipeline.py` 里**没有「章节」概念**：`extractor.extract()` 把整本 PDF 拍平成一个字符串，
`body()` 定位正文起点，然后 `scriptwriter` 里 `[:2500]` 一刀切。

后果：一本 348 页的书 → 只出**一条 12 句的视频**，且只用了开头 2500 字。目录、章节结构全被丢弃。

目标：**书 → 目录树 → 按章点播 → 每章一条片**，且同一章重跑不重算。

## 二、四个探针（先量再优化）

### 探针 1 · PDF 自带目录树，索引零成本

```
页数: 348
outline 顶层条数: 35      总条数: 93
[p27] 第1章 何谓关键对话
  [p30] 人们通常是如何应对关键对话的
  [p38] 本书的大胆主张
  [p49] 小结
[p50] 第2章 掌握关键对话
  ...
```

**结论**：`pypdf` 的 `reader.outline` 直接给出两级目录 + 精确页码，**无需模型参与**。
零成本、零幻觉、毫秒级。有页码即可精确定位每章文本范围（p27–p49 = 第 1 章）。

兜底链：`outline` → 正文「第X章」正则（实测前 20 页命中 11 条）→ 整本当一章。
**不再用 `body()` 的正则猜测当主路径。**

### 探针 2 · LLM 请求无法并行（Ollama 服务端串行）

| 方式 | 耗时 | 结论 |
|---|---|---|
| 串行 2 请求 | 2.2s | — |
| 并发 2 请求 | 2.1s | 省 5% = 噪声 |

**结论**：给 Ollama 加线程池是无效优化。**它一次只算一个请求。**
想省 LLM 时间只有两条路：**缓存复用**（不重算）或**减少调用**（批处理成一次调用）。

### 探针 3 · 真正的瓶颈分布（颠覆直觉）

| 环节 | 实测 | 占比 | 能否并行 |
|---|---|---|---|
| LLM 分镜（think=true，12 句） | ~36s | 48% | 不能（探针 2） |
| **TTS（12 句串行）** | **28.9s** | **39%** | **能，纯网络 IO** |
| 渲染 12 张卡 | **2.0s** | 3% | 能，但不值得 |
| 抽取 + 合成 + IO | ~8s | 10% | 小头 |

直觉会去优化「渲染 12 张图」（以为很慢）和「上多线程调模型」——
**两个都不是瓶颈**：渲染 2 秒（0.17s/张），模型不给并行。

### 探针 4 · TTS 并发有效，13x

| 方式 | 耗时 | 成功 | 加速 |
|---|---|---|---|
| 串行 12 句 | 28.9s | 10/12 | — |
| 并发 6 线程 | 5.7s | 11/12 | 5.1x |
| **并发 12 线程** | **2.2s** | **12/12** | **13.1x** |

**结论**：这是整条链路最大的白捡收益。12 并发未见限流（12/12 成功）。
工程上仍需：失败重试 + 失败率升高时自动降并发（`ponytail:` 标注上限）。

## 三、性能账

| 环节 | 现在 | 优化后·首跑 | 优化后·重跑（缓存命中） |
|---|---|---|---|
| LLM 分镜 | 36s | 36s | **0s** |
| TTS | 29s | **2.2s** | **0s** |
| 渲染 | 2s | 2s | 2s |
| 其他 | 8s | 8s | 8s |
| **合计** | **~75s** | **~48s（省 36%）** | **~10s（省 87%）** |

「重跑」指：改了某句话 / 换了配色 / 只调封面。**这是迭代期的常态操作**，
缓存命中后从 75 秒变 10 秒，比任何"极致优化"都实在。

## 四、架构

### 4.1 模块分层（依赖单向，无环）

```
                    models.py          数据契约：Scene / Chapter / Outline / Job
                        ↑              所有人依赖它，它不依赖任何人
    ┌───────────────────┼───────────────────────────┐
extractor.py        outline.py              cache.py
（文件→页文本+页号）  （目录树，outline优先）    （内容哈希→产物复用）
    └────────┬──────────┘
             ↓
        segmenter.py       章节 → 文本片段（按页码范围，不再 [:2500]）
             ↓
        scriptwriter.py    LLM：片段 → Scene[]
             ↓
    ┌────────┴────────┐
visualizer.py      narrator.py
（Scene→PNG）      （Scene→MP3，含 speak_many 并发）
    └────────┬────────┘
             ↓
        compositor.py      媒体 → MP4（FFmpeg，已就绪）
             ↑
        pipeline.py        只做编排 + 缓存判断 + 进度，不实现任何环节
```

**关键改动（高内聚低耦合）**

| 改动 | 为什么 |
|---|---|
| 新增 `models.py` | ⚠️ **本文初稿此处判断有误，已更正**：原写「`Scene` 被 `visualizer`/`narrator` 导入 → 反向依赖」——全仓检索后**不成立**（二者只 import `pathlib`/`PIL`/`.icons`/`binpaths`；唯一实例是测试脚本 `tools/probe_perf.py:37`）。**真实理由有三**：①**契约所有权错位**——`Scene` 是「生成→画面→配音」三方对齐的契约，却定义在生成层 `scriptwriter.py` ②**裸 tuple 契约**——`compositor.compose()` 收 `list[tuple]`，靠位置对齐，调换顺序不报错只出错片 ③**无序列化契约**——`script.json` 要能人工改，需要稳定 schema。详见 `specs/2026091518-book2vido-chapter/01_analysis.md` §二 |
| 新增 `outline.py` | 「DOM/PDF 结构 → 章节树」是独立职责，塞进 extractor 会变成一个文件两件事 |
| 新增 `segmenter.py` | 「章节 → 片段」的切分策略独立可测，也是 `[:2500]` 一刀切的替换点 |
| 新增 `cache.py` | 缓存策略独立，便于整体关闭（`--no-cache`） |
| 新增 `providers.py` | 实施期追加：把「造 provider」从 pipeline 拆出（AC-16 暴露的关注点混杂） |
| `extractor.py` 减负 | 只保留「文件 → 页文本 + 页号映射」。⚠️ **实施时未删 `body()`**：项目回滚条件是「只增不删」，且 `RuleFallbackProvider` 降级取料仍在用 → 改为**标 deprecated 保留** |
| `narrator` 加 `speak_many()` | 并发是 TTS 自己的事，不该由 pipeline 拼线程池 |
| `pipeline` 拆函数 | `run_chapter()` / `run_book()` / `run()`，避免长成上帝函数 |

### 4.2 缓存目录

```
cache/<书内容哈希>/
  outline.json        目录树（探针 1 产物）
  ch01/
    script.json       LLM 分镜结果 ← 最贵，必须缓存，且可手工编辑
    card_01.png ...   画面
    voice_01.mp3 ...  配音
    ch01.mp4          成片
```

三层命中语义：
- 全部命中 → 直接返回 mp4（~0s）
- `script.json` 命中、画面/配音缺失 → 跳过 LLM（省 36s），只重渲染
- `script.json` 被手工改过（哈希变化）→ 重跑下游，**不动 LLM**

### 4.3 CLI 形态（先 CLI，网页最后）

```bash
book2vido outline book.pdf            # 建索引，秒出
book2vido list book.pdf               # 打印章节树
book2vido run book.pdf --chapter 3    # 只生成第 3 章
book2vido run book.pdf --chapters 1,3,5
book2vido run book.pdf --all --jobs 4 # 全本（章级串行，章内并行）
```

`--jobs` 只控制 TTS 并发度，**不控制 LLM**（探针 2：控了也没用）。

## 五、工程化约定（AI 友好 + 可微调）

| 约定 | 具体做法 |
|---|---|
| 单一职责 | 每个模块 <200 行（例外 `icons.py` 311 行的映射表，纯数据不算逻辑） |
| 数据契约 | 跨模块传递一律用 `models.py` 的 dataclass，不用裸 `tuple`（现在 `media` 是三元组） |
| 注释写「为什么」 | 例：`# 必须显式声明 think：qwen3 在 Ollama 里默认开启，不写=行为随版本漂移` |
| 中间产物落盘 | `script.json` / `outline.json` 可读可改 → **人工微调的口子**：改完跳过 LLM 直接重渲染 |
| 可观测 | 每章每步打印进度（军规 progress_visibility），失败不静默 |
| 自检 | 非平凡逻辑留一个可运行检查（`python -m book2vido.outline book.pdf` 能直接跑） |

**给 AI 改代码的额外好处**：模块边界清晰 + 契约显式 → 改一个文件不牵动全身，
模型不需要一次读完整库才能动手。

## 六、不做的事（连同理由）

| 不做 | 理由 |
|---|---|
| 引 Celery / Prefect / Ray / Airflow | 给「12 句视频」上分布式任务调度是负收益。标准库 `concurrent.futures` + 文件系统足够 |
| 并行 LLM 请求 | 探针 2：服务端串行，省 5%（噪声） |
| 并行渲染 | 探针 3：全量 2s，不值得引入复杂度 |
| 章级流水线（A 章配音时 B 章推模型） | 理论省 34%，但 TTS 并发后只剩 8% → 不划算 |
| 网页「点播」界面 | 先跑顺 CLI。界面是薄壳，等 CLI 稳定后再套 |
| 「极致性能优化」这个目标本身 | 首跑 48s、重跑 10s 已够用。再加优化就是给非瓶颈写代码 |
| 把整章原文全喂给模型 | 4K 上下文硬约束。超长章由 `segmenter` 采到 2500 字以内 —— **代价见下** |

### ⚠️ 采样的代价：章节越长，盲区越大

`segmenter.slice_chapter` 对超长章走「首/中/尾各 1/3 预算」采样，单章输入恒 ≤ `limits.max_chars`（默认 2500）。
**这不是缺陷，是 4K 上下文下的妥协** —— 但它带来一个**反直觉的后果**（《关键对话》348 页实测）：

| 章 | 页数 | 原始字符 | 喂进模型 | 覆盖率 |
|---|:--:|---:|---:|---:|
| 第1章 | 23 | 10,213 | 2,498 | 24.5% |
| 第2章 | 17 | 7,978 | 2,498 | 31.3% |
| **第3章** | **25** | **10,201** | **2,498** | **24.5%** |
| 第5章 | 40 | 16,879 | 2,498 | **14.8%** ← 最低 |
| 第7章 | 36 | 14,423 | 2,498 | 17.3% |
| 第9章 | 18 | 6,116 | 2,498 | 40.8% |
| 第11章 | 14 | 5,384 | 2,498 | 46.4% |

**规律：章节越长，进模型的比例越低。** 最长的第 5 章（40 页）只有 **14.8%** 进了模型 ——
12 句口播稿是从**不到六分之一的原文**里提炼的。短章（< 2500 字）则 100% 进。

> 📌 **读日志时的坑**：`· 正文切片：2498 字（上限 2500）` 里的数字是**输入**，不是分镜大小，
> 也不是章节原文长度。分镜大小看的是「12 句」。历史上有过一行写成「分镜：N 字」的日志，
> 导致把输入字数误读成分镜字数（错题库 **L-17**）。

**复现命令**（口径可核对）：

```bash
PYTHONPATH=src python - <<'PY'
from book2vido import extractor, outline, segmenter
SRC = "<书>.pdf"
pages = extractor.resolve_pages(extractor.lazy_pages(SRC))
doc = outline.build(SRC)
for ch in doc.chapters:
    if not ch.index:
        continue                      # 0 = 小节，跳过
    raw = len(segmenter._chapter_text(pages, ch))
    txt = len(segmenter.slice_chapter(pages, ch, 2500))
    print(f"ch{ch.index:>2} p{ch.start_page}-{ch.end_page} 原始{raw:>6} 切片{txt:>5} {txt / raw:>6.1%}")
PY
```

**想提高覆盖率怎么办 —— 先过铁律七的三道闸**：

| 想法 | 判 |
|---|---|
| 调大 `max_chars` | ❌ 超 4K 上下文，本地 8B 会截断/失焦 |
| 分多次调用模型再合并 | ❌ **调用次数 ×N** —— 违背铁律六「把模型算力花在真正要判断的地方」 |
| 换长上下文模型 | △ 违反铁律二（本地 16GB 跑不动更长的） |
| **接受上限，但让它可见** | ✅ 本节的表 + 日志里的「上限」提示 —— **上限是设计，不是缺陷** |

⚠️ 只有在实测证明「12 句没抓住章的重点」时才值得重估。
**判据**：拿该章**末尾**的内容去问，看分镜里有没有 → 全无 = 盲区真的伤到了，再谈方案。

## 七、实施顺序（每阶段可独立验收）

| 阶段 | 内容 | 验收标准 | 状态 |
|---|---|---|---|
| P1 | `models.py` + `outline.py` + CLI `outline`/`list` | 能打印出 348 页书的完整章节树 | ✅ 实测 `top()=22`、合计 93 |
| P2 | `segmenter.py` + `run --chapter N` | 第 3 章能独立出片，时长/句数合理 | ✅ 第 3 章 12 句 / 39.7s |
| P3 | `narrator.speak_many()` 并发 | 12 句 TTS 从 29s 降到 ~3s，成片音画同步 | ✅ 1.87s（8.7x） |

| P5 | （可选）单文件网页点播 | 点章节 → 生成 → 播放 | ⬜ 未做 |

P1–P4 是「目录索引 + 按需生成 + 该有的性能」的完整闭环，P5 是锦上添花。
