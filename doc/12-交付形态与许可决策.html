02依赖许可审计（选协议之前必须先做这个）

为什么先做这个：你给自己代码选什么协议，管不了你随包分发别人的二进制。 如果包里带了 GPL 的 ffmpeg，那这份分发包就有 GPL 的分发义务——**不管你自己的 LICENSE 写了什么**。

03开源协议：四个选项

一个容易被忽略的事实：现在什么都没分发出去，所以此刻改协议的成本是零； 一旦有人在 MIT 下拿到代码，就收不回来了。这是最便宜的决策时点。

推荐 · 现在A · 私有仓，暂不授权源码
做什么仓库私有（就是你刚拍板的这条）；LICENSE 换成「保留所有权利 / 源码可见但不授权使用」。
交付只分发安装包。**内容分发不需要开源源码。**
成本0
代价少了一份"GitHub 作品集"资产。
将来B · 分层开源（引擎开 / 产品闭）
做什么Python 引擎层（抽取 / 分镜 / 画面 / 配音 / 合成 / 缓存）开源；打包脚本、图标资产、未来 UI 与品牌资源保留。
协议引擎层 Apache-2.0（专利授权明确、商用友好、便于被引用）。
好处拿到 IP 收益与潜在贡献，同时保住产品层的独占。
注这条与你 `CONSTITUTION.md` 铁律五原本的写法一致（"引擎 MIT 开源"）。
谨慎C · 全开 MIT / Apache-2.0
现状磁盘上的 LICENSE 现在就是 MIT。
好处传播最大，最容易被别人拿去用。
代价永久放弃"独占商业化"——任何人都能直接拿去卖。对一个"想卖钱"的念头来说，这是最贵的一条路。
将来D · 全开 AGPL-3.0 + 商业授权双轨
逻辑AGPL 让"拿去改一改做成云服务卖"这条路走不通，而你**自己**可以卖商业授权。
好处既开源、又保住收钱的口子。Grafana 一类走的这条路。
代价AGPL 会吓退一部分使用者与贡献者（尤其公司环境）。

为什么推荐 A，而不是直接把 MIT 执行下去

  • 开源的主要收益，现在拿不到：外部贡献者和生态需要"有用户"作为前提。n=1 的项目开源，换来的是无人问津加一份维护承诺。
  • 一键安装包 + 内容分发不需要开源：你要的交付形态是"给不懂技术的人一个包"，这条路和源码可见性无关。
  • 公开不可逆，私有可逆：不开源保留了"将来开"的期权；开了就放弃了"将来不开"的期权。**期权在不确定时更值钱。**
  • 在职状态下的痕迹是永久的：仓库里曾有文件含 /Users/<用户名> 绝对路径、另有文件字面写了 CodeMax。绝对路径已于 2026-09-16 全库清理（口径：git grep -lE '/Users/[^/]+/'）；CodeMax 一项仍未处理。私有无碍，公开就是可定位指纹。引用这类计数前先重跑口径命令——每写入一个相关文档，它就会变。
  • 最少遗憾原则：万一将来你决定开源，今天什么都没损失；万一你决定商业化，选 C 就损失掉了。

04需要显式裁决的一处冲突

你的项目宪法里已经写过一次答案，而且和现在的想法不一致——这个必须你亲自拍。

位置原文口径与本决策的关系
CONSTITUTION.md 铁律五 「引擎 MIT 开源；内容模板 / 工作流 / 宣发 SOP 闭源。护城河 = 极致省资源方法论 + 人设 + 素材库，不在技术拼装本身。」 与当前倾向冲突。
铁律五的判断是"技术拼装不是护城河，所以可以开源"；
而新信息是"这个项目可能有商业化价值"。两者不是对错，是信息变了。

我的建议：把铁律五改成「引擎层将来可按 Apache-2.0 / AGPL-3.0 分层开源；产品层与品牌资产保留； 在明确商业化边界之前，不公开分发源码。」——这样既没有否定原判断（引擎确实不是护城河）， 又给"想清楚"留出了时间。改宪法属于规则类变更，你点头我就直接落库并回写 CHANGELOG。
