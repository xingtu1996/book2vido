02商业化信号：三条，但都不是"现在就做"

原话保留，人物以角色代称。

运营侧

「有技术有运营，可以搞」

读法：这是本次唯一一次"合作可行性"判断。它成立的前提是两个人真的各自能补上对方缺的那一半—— 不是"有个想法"。目前看前提成立。

技术侧

「我咋感觉这个产品做出来，研究一下，还能卖钱呢。上架 app store 这种。」

读法：方向直觉，不是决策。它把"能卖"和"上架 App Store"绑在了一起，而这两件事可以拆开。

技术侧（半分钟后自己收回来）

「管他呢，反正就是能做出身边少数几个爱不释手的 APP 就行，后面再看看商业化啥的是不是能运营一下。」

读法：这句话里的验收标准比上面那句成熟得多—— n = 5~10 个真人愿意持续用，是一个当下就能验的标准，不需要上架。

03三个架构问题：先回答能定死的

三问都来自同一次群聊，且都能用现有代码与实测数据回答，不需要"以后再说"。

Q1　手机端和电脑端，是通用一个模型，还是各用各的？——先看有没有本地算力

  • 本地模型 qwen3:8b 权重 5.2 GB，本机 16 GB 内存实测可跑；手机端没有 Ollama， 也没有等价的内存预算给它。
  • 「手机本地跑小模型」这条路在质量上必然退化到不可用——同一任务把 think 关掉（算力需求降低） 结果是"快 2 倍但句子明显变碎"。模型变小是同一类退化。
  • 书和 PDF 都在电脑侧，手机侧没有生成场景。
结论：不是"两端各用不同模型"，是一个内核、两种消费——电脑生成，手机看片。 真要做移动端生成，走"用户自带 API Key 打远端"，而不是往手机里塞小模型。

Q2　做全平台的话，语言架构是不是都不一样？——现状已经是三层分离

  • 现有结构：Python 内核（跨平台）＋ 平台二进制（Ollama / FFmpeg，两者都有官方多平台版）＋ 薄壳（macOS .app 115 MB，自检 7/7 绿）。
  • binpaths.py 已经把二进制路径抽成一层，原先 4 处硬编码（ffmpeg / ffprobe / rsvg / DYLD）已清掉—— 这是跨平台最脏的活，已经做完了。
结论：不存在"架构不一样"。一套内核 + 各平台各自的二进制与壳。 真正的分岔只有一条：这一端有没有本地算力。
平台本地算力改造量判断
macOS有已通已可用
Windows有估算 1–3 天打包脚本 + 拖拽/路径适配
Linux有估算 1 天可忽略（无用户）
iOS / Android无属真重构跑不了 Ollama / FFmpeg，除非走远端 API

Windows / Linux 的工期为估算，尚未实测，不作为承诺。

Q3　支持传自己的 API Key、接三方 AI（类似闪电说）？——地基已经在了

  • 架构里已有 Provider 抽象：scriptwriter.LLMProvider / OllamaProvider / RuleFallbackProvider； narrator.TTSProvider / EdgeTTSProvider / SayProvider。
  • 装配点只有一处：providers.py:26-35 按 cfg 里的 provider 名造对象。
  • 所以接三方 = 新增一个类 + 一个分支。这套抽象当初是为"没模型时能降级跑"做的， 正好就是"接三方"的地基——不用改上层任何逻辑。
建议照抄闪电说被验证过的三条信任路径叙事： ①本地模型（免费、隐私，声音和数据不出机器）②自接 Key（你的 Key 直连服务商，不经过我们） ③我们的转发 / 会员（早期不做）。它在官网上敢写"接自己的模型，一直免费"， 这句话本身就是它的信任来源。

但要分清两件事：用户自带的 Key 是用户的自由；我们自己的代码里绝不能出现任何公司 Key—— 这条已有红线，且有 AC-15 的关键词扫描守门。

04推荐路线：内容优先，产品后置

先给结论，再给代价。

推荐A · 内容优先
做什么把项目本身做成 3–5 篇内容（公众号长文 + 贴图 + 视频号）， 用「半分钟 / 不到 1MB / 不要钱」当钩子；App 只作为文章末尾给朋友的下载链接。
成本0 元（不含时间）
收益账号增长——你现在最缺的东西。
风险选题对但渠道弱，可能不涨粉。
可并行B · 产品优先（小圈子）
做什么Mac 版先给 5–10 个人用，收反馈，不谈上架。用"身边几个爱不释手"当验收。
成本维护时间（每次系统升级都要跟着修）
风险没人真用则时间白投。判据：有没有 ≥3 人主动天天开。
不建议现在做C · 上架 App Store
成本$99/年 + 审核 + 隐私政策合规 + 跨平台维护 + 客服
风险把一个冷启动账号最稀缺的资源（你的时间）投进一个零线索渠道。
另上架 = 显性副业收入，与在职状态的红线直接冲突（见 §05）。

为什么推荐 A：四条理由，都锚在现状上

  • 账号阶段：公众号仍在冷启动，近期靠大会带来 25 个新粉（此前 20）。 这个阶段该买的是"被看见的次数"，不是"上架"。
  • 验收标准已经是对的："身边少数几个爱不释手的 APP"——n = 5~10 个真人， 不需要上架就能验。上架反而把验收推迟了几周。
  • 在职状态：上架即显性副业收入，劳动合同 / 竞业条款风险； 且项目与职业身份的关联信息一旦公开，就是可定位的指纹。
  • 项目天然是内容：「我把一本书半分钟变成能看完的视频，零成本、全本地跑」—— 这是"工具 + 反直觉数字 + 可复现"的爆款结构。项目本身就是最好的素材。

A 的代价，以及怎么补

  • 代价一：工具型内容容易引来同行，而不是普通读者。 补法：钩子用"这本书讲了什么"，不要用"我用了什么技术"。
  • 代价二：正文若写成技术汇报，普通人看不下去——那正好和产品要解决的问题自相矛盾。 补法：文章主角是书里的观点，工具只是容器（利他 > 炫技）。

05红线清单（商业化之前必须先过这四关）

  • 脱敏：本看板及后续一切对外物料，不含真实姓名、雇主名称、内部项目代号。本文件已按此处理。
  • 在职：上架、收款、公开招募等商业化动作暂停，直到边界明确。
  • Key：行途内容生产不接公司任何 LLM / API Key（已有 AC-15 扫描守门）。
  • 合伙：技术 × 运营目前是口头约定。真要走商业化，第一件该定下来的 不是代码，是"谁的账号上架、收入怎么分、不做了怎么退"。

06顺带发现：slogan 的数字对不上实测

slogan 是要对外说的，数字必须扛得住核。

另：samples/g/ 是 --chapters 1,3,5 的真实多章产物（三条均合法：h264 1080×1920 + aac）， 不是垃圾文件。但目录名没有含义，建议改名为多章能力证据保留。
