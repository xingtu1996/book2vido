极致简单：外部端优先，还是先把包交付出去？

book2vido · 2026-09-20 · 基于本机实测 + 仓库现状的决策看板
结论：同意"先把外部端做好"——但要先承认一件事：在 ffmpeg 没随包之前， 界面做得再好也交付不出去。 所以真正的顺序是 P0 打通可交付性（约半天）→ P1 外部端闭环 → P2 降门槛。 P0 不是"降门槛"，它是"让后面所有投入都有对象"。

1你的类比重构：它俩不是靠"小巧"赢的

你说"Work Agent / Coding Agent 看着小小，但要本地启动、安装成本太高"。这句话对，但根因不在"有没有界面"：

维度Work Agent / Coding Agentbook2vido 现状（实测）
安装动作npm i -g 一步完事装 Ollama + 拉 5.2 GB 模型 + ffmpeg + Python 运行时
依赖是否在包里是（随包下载）ffmpeg 不在包里（packaging/ 只有 36 KB 脚本，无 vendor/）
首次见到界面前一条命令读完 README 的"⚠️ 还不能交给没有技术背景的人"

所以矛盾的本质是「依赖不在包里」，不是"有没有 GUI"。 这也解释了你感觉到的那股别扭：这个项目内核已经很轻（7 环节只有 1 环节用模型）， 但外面套的安装壳很重 —— 轻的东西被重壳压住了。

3三阶段路线

P0 · 让包真的能交付出去（硬阻塞，建议今天清点）最高优先
注入 static 版 ffmpeg（不能用 brew 版，它绑 18 个 dylib 不可分发）+ 过 build_app.sh --check 门禁。 在此之前，任何界面投入都只能你自己用。
产出：一个双击能给别人用且不崩的包。这是"外部端"存在的物理前提。
P1 · 外部端闭环（你说的"可视化帮我完成全部操作"）优先做
把一次完整操作全程可见：选文件 → 看章节树 → 选章 → 预览分镜 → 出片 → 结果显示/重试/历史。 关键是反馈不是按钮：现在后端会按阶段发通知，但界面上看不到"进行到哪一步、还要多久"。
待拍板：Web 前端（零依赖单文件 HTML + 本地 http server，可复现现象路线，启动一条命令） vs 原生桌面壳（更像产品，但投入量级完全不同）。见下一节。
P2 · 降门槛（门槛清单，按性价比排）后置
  • 首次启动向导：把"下载模型（约 4.9 GB，预计 X 分钟）"讲清楚 + 进度条 —— 成本最低、体感提升最大
  • 默认模型瘦身：先给一个小模型跑通全流程，让用户 5 分钟内看到第一条片，再提示可升级 8B 提升质量
  • 一键体检按钮：已有 tests/verify_env.py，界面直接调用它，用户不必懂 PATH / 依赖

4需要你拍板的一件事：外部端做成什么形态？

A · Web 前端（单文件 HTML + 本地服务）推荐

  • 沿用 tools/ollama_webui.html 已验证的技术栈（零依赖、单文件、本地 http://127.0.0.1）
  • 浏览器就是 UI，不用学桌面框架；Mac/Windows/Linux 同一份代码
  • 启动一条命令，或打包时让 launch 脚本自动开浏览器 → 用户体验≈桌面 App

代价：需要用户理解"它在本地起了个服务"（向导里一句话说清即可）

B · 原生桌面壳（Swift / Tauri）

  • 最像成品 App，可接受拖拽、菜单栏、通知等系统能力

代价：新语言/新工具链进项目，与"克制"铁律和三道闸冲突；且在 ffmpeg 未随包前，做出来也发不出去

我的建议：先 A 跑通闭环，B 等有人真在用之后再议

理由不是"A 简单"，而是 现在最大的未知不是界面形态，而是"谁会用、用来干什么" —— 在 n=1 的阶段，用最低成本把闭环铺出來，比提前押注形态更稳。 真正该先花钱的地方是 P0（可交付性），那里没有选项，只有做和没做。

5公开前不可跳过的三件事（发之前一分钱，发之后无穷贵）

只要目标是"给别人用"，下面三条必须在第一次分发出去之前闭环，任何一条遗漏都不可逆：

  • ① 脱敏扫描 —— 绝对路径 / 本机用户名 / 内部代号（判据是"这些细节组合起来雇主能不能认出我"）
  • ② LICENSE 裁决 —— 磁盘上现在是 MIT，推荐路线是"私有 + 暂不授权源码"。此刻改成本为零，分发出去不可收回
  • ③ 换掉 demo 里的受版权素材 —— 现用的是真实出版物
