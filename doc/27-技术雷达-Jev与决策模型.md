# 27 · 技术雷达：Jev / NanoJev 与「决策模型」这一新物种

> **本文只回答一个问题：这个新东西要不要接进 book2vido？**
> 结论写在最前面 —— **不接**。理由在 §四。
> 但它的出现**改变了我们对「哪一格该用模型」的判断框架**，所以值得留档。
>
> 实测/核实日期：2026-09-19（Jev 发布第 4 天）。

---

## 一、它是什么（多方交叉核实后）

**Jev** = TypeSafe AI 的第一个 **System One 模型**，2026-09-15 随公司出隐身一起发布。

| 事实 | 值 | 备注 |
|---|---|---|
| 公司 | TypeSafe AI（旧金山） | 出隐身同时 $40M seed（DCVC 领投），估值约 $2 亿 |
| 创始人 | **Diogo Almeida**（CEO） | 前 OpenAI，InstructGPT 一作、ChatGPT 贡献者、Google Brain 经历 |
| 核心主张 | 软件不需要模型「说话」，需要它**做决定** | 不生成任何文本 |
| 输出原语 | **Choice**（2–255 选一）/ **Boolean**（官方叫 Noul）/ **Score**（2–10 级有序量表） | 带校准概率 |
| 训练方法 | **RLCD**（Reinforcement Learning for Calibrated Decisions） | 优化目标：0.8 置信 ≈ 80% 真对 |
| 延迟 | 70–500 ms（厂商自报） | 对比对话式前沿模型 3–329 s |
| 定价 | 输入 $0.042/百万 token，**输出免费** | 因为「没有输出可计费」 |
| 名字由来 | 经济学家 William Stanley Jevons（杰文斯悖论） | 决策变便宜 → 用量暴涨 |

**NanoJev** = 社区对 Jev 的**开源复现**（不是官方，也不还原真实架构）。

| 事实 | 值 |
|---|---|
| 仓库 | GitHub `TianyuCodings/NanoJev` · HuggingFace `C-Tianyu/NanoJev`（权重 + 数据 + 训练管线全开源） |
| 底座 | **Qwen3-0.6B**（与本项目的 `qwen3:8b` 同一家族，但小一个量级） |
| 核心改动 | 把 LM head 整个换成 **decision head**：LayerNorm + Linear(d_model, 1)，每个候选出一个标量 logit，同问题候选做一次 softmax |
| 实测 | 50×50 迷宫 244 步 / 36 次碰撞到达终点；12×12 贪吃蛇吃到 27 个食物存活 256 步 |
| Benchmark | 4×4 测试图：NanoJev **95%** vs Jev **100%** vs 未微调 Qwen3-0.6B **35%**；OOD 6×6：90% vs 95% vs 15% |
| 运行环境 | ⚠️ 官方要求 **CUDA** 环境（`requirements-toy.txt`） |

## 二、三条必须纠正的转述错误（营销号视频口径）

boss 带来的视频摘要里有三处与原始信源不符，**核实后记录在此**（这也是「术语 SSoT」纪律的用武之地）：

| # | 视频说法 | 事实 |
|---|---|---|
| 1 | 「NanoJev 性能**反超**原版 Jev」 | ❌ **没有反超**。官方 benchmark 上 NanoJev 95%/90%，Jev 100%/95% —— 是**逼近**，不是超越 |
| 2 | 「首创**前缀树注意力机制**」 | ❌ 查无官方出处。**Jev 架构至今未公开**。NanoJev 作者自己声明：这是「面向同一接口、能自洽跑起来的一种实现」，**不是 Jev 真实架构的还原** |
| 3 | 创始人 **Diego** Almeida | ❌ 同名污染（语音转写同音词）。正确写法 **Diogo**（葡萄牙语名） |

> 另：厂商自报的「193.6x 快 / 444.6x 便宜」是**公司自建基准**（以两个外部大模型的平均答案为标准，而非标准答案）。
> 独立测试（Every）在同任务上只测出约 **25x** 快。
> **引用这类数字时必须标注「厂商自报」** —— 否则就是替厂商背书。

## 三、为什么它仍然重要（改变的是判断框架，不是我们的链路）

Jev 的价值不在「更快的模型」，而在**把「决策」从「生成」里拆出来**这件事本身：

```
传统做法：让 LLM 生成一段话 → 解析成 JSON → 校验 → 重试（慢、贵、会格式错）
Jev 做法：状态 + 类型化问题 → 直接给概率分布（无解析、无格式错、置信度可用）
```

它点破了一个长期被忽略的成本：**大量 Agent 环节其实只需要一个 if 判断，却租了一整台对话模型**。
模型路由、工单分派、结果排序、上下文过滤、安全校验 —— 这些都是高频窄决策。

## 四、裁决：不接入 book2vido（四条理由）

| # | 理由 | 说明 |
|---|---|---|
| 1 | **类型不匹配** | book2vido 唯一用模型的一格是**分镜 = 文本生成**（把长文压成 12 句口播稿）。Jev/NanoJev **不生成文本**，物理上做不了这件事 |
| 2 | **违反铁律六** | 宪法规定 7 个环节只有分镜一格用模型。链路上的「决策类」环节（选章、断句、配图标）现在是**规则代码** —— 规则是确定的、可复现、零耗时。换成模型 = 主动把确定性换成漂移，且要多一层缓存 |
| 3 | **本机跑不了** | NanoJev 官方要求 **CUDA** 环境。本机是 **Apple M1 Pro**（Metal/MPS），无 NVIDIA GPU，官方未适配 → 不是「慢一点」，是**跑不起来** |
| 4 | **收益为负** | 受控概念词表（85 词）已经把「关键词 → 图标」的语义命中率修好了（`doc/08`）。用 0.6B 决策模型替换它，换来的是模糊匹配能力 —— 而我们要的恰恰是**不模糊** |

**一句话**：它是给「高频窄决策」用的引擎，而 book2vido 的瓶颈是「一次性文本压缩」。
两件事长得很像，但不是一件事。

### 唯一值得观察的契合点（列入观察，不动手）

`visual` 层的**图标语义匹配**目前依赖受控词表（硬匹配，新词命中不了会降级为「首字大字」）。
理论上 Choice 原语可做「模糊语义就近匹配」。
**但**：① 违反铁律六 ② 本机跑不了（CUDA）③ 词表方案已够用 ——
三条任一成立即不接（铁律七：最省的依赖是不引入的那个依赖）。
**触发重评的条件**：NanoJev 出现 MPS/MLX 移植 **且** 词表命中率实测低于某阈值。在此之前不动。

## 五、那它对本项目的价值是什么

**内容侧，不是技术侧。**

- book2vido 的定位是「**思想的搬运工**」：输入长文 → 出视频。Jev/NanoJev 的科普长文，正是它的**输入素材**。
- 换句话说：这条链路可以**用它自己讲它自己没接的一个技术** —— 输入一篇《Jev 是什么》的稿子，出一条短视频。
- ⚠️ 宣发 SOP / 内容模板**不属于本仓库**（README「不变的部分」）。本仓只负责：它能出片，且出片不需要它。
