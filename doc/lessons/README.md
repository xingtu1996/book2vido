# 错题库 · book2vido Lessons

> **这本是干什么的**：项目里踩过的坑，一条一条留档。目的不是"记录历史"，是让**同一个坑不要再踩第三次**。
> 本项目已经出现过**同一类缺陷连续复发**（术语 / PNG / 分镜 / 构建）的情况——所以光记在聊天里不够，得有一本能被翻的账。
>
> **怎么用**：写代码前扫一眼 §一 总表；提 PR / 发布前把 §三「复发判据」当检查清单过一遍。
> 判据都写成**能被一眼认出的样子**，不是抽象原则。

## 二、逐条详情

<a id="l-01"></a>
### L-01 · 宣称"12/12 语义命中"，实为"12/12 有图标"

- **现象**：对外/对己都记着"图标语义命中 12/12"，出片后肉眼核对发现首版 12 张卡只有 **6 个不同图形**（拼图撞 3 次、菱形 2 次），语义相符不到 1/3。
- **真因**：**指标定义错位**——统计的是"有没有图标"，被当成了"图标对不对"。根因在架构：让 LLM 自由出词、再事后翻译成图标。
- **修法**：①把**受控概念词表前置**进 LLM 输出约束；②指标改名，别让"有"冒充"对"。
- **复发判据**：任何"命中率 / 成功率 / 覆盖率"出现时，追问**分子分母到底是什么**，并**实图/实物核对**一次。
- **证据**：`doc/08-画面资产策略.md` §六；`samples/画面层修复前_12卡总览_20260915.png`。

<a id="l-02"></a>
### L-02 · 手改分镜被静默丢弃

- **现象**：手工改了 `script.json` 里一句口播稿，重跑出来的**还是老视频**。
- **真因**：`video_key` 挂的是**输入文本**派生的 `script_key`。手改的是**输出文件**，输入没变 → 键不变 → `hit_video` 命中**旧分镜渲染的成片**。用户的改动被静默丢弃。
- **修法**：`video_key` 改挂 `sha256(分镜规范化 JSON)` 指纹。改一句 → 只重渲染下游，LLM 不跑。
- **复发判据**：**凡"用户能手工改的文件"，它的内容指纹就必须进下游缓存键。** 问一句：改了这个文件，谁的下游该失效？答不上来就是坑。
- **证据**：`src/book2vido/cache.py` `video_key()` 文档字符串；`specs/2026091518-book2vido-chapter/03_design.md` §3.3。

<a id="l-03"></a>
### L-03 · "全命中"却要等 19.9s

- **现象**：三层缓存全命中，日志显示内部耗时 0.0s，但墙钟 19.9s。
- **真因**：命中路径**仍在做无用功**——`extract_pages()`(5.9s) 解析全书 348 页 + `outline.build()`(6.0s) 重建目录。只算了"要不要重做"，没算"命中时顺手做了多少不该做的"。
- **修法**：①`outline.json` 优先读缓存；②章切片落 `text.txt`；③`extractor.lazy_pages()` 把抽页**延迟到真正需要时**。→ **19.9s → 0.5s**。
- **复发判据**：**"全命中"的耗时应当接近「读文件 + 判断」的开销。** 若仍是数秒，就是白算。
- **证据**：`specs/2026091518-book2vido-chapter/01_analysis.md` §七。

<a id="l-04"></a>
### L-04 · 文档承诺的"人工可改口子"是假的

- **现象**：设计文档写"`outline.json` 落盘 = 人工可改的口子"，实际手改完全不生效。
- **真因**：每次 `run_book` 都**重建** outline，`save()` 落的盘白存——**文档描述了实现里根本不存在的性质**。
- **修法**：改成优先 `load()`，手改即生效。
- **复发判据**：**凡是文档写"可以手工改 X"的地方，必须真的手改一次、重跑一次、看它变了没有。** 没实测过的"可改"一律按不存在处理。
- **证据**：同 L-03。

<a id="l-05"></a>
### L-05 · 目录页被当成正文页

- **现象**：正则兜底扫描时，「第 10 章」的起始页被取成了目录页 p007。
- **真因**：判据是「页内章标记 ≥3 条」，但目录行尾部带点线引导符 + 页码（`第 10 章 案例分析……143`），**长度超出正则上限而匹配失败**——实测只命中 2 条，阈值 3 就漏了。
- **修法**：换成**与标记数量无关**的判据——「行数 ≥8 且半数行 ≤25 字」（目录长得像清单，正文是 40–70 字段落）。
- **复发判据**：**判据依赖的那个数量，去数一遍真实样本。** 靠"大概能命中几条"设的阈值，一定会在某个样本上失效。
- **证据**：`src/book2vido/outline.py` `_looks_like_toc()`。

<a id="l-06"></a>
### L-06 · 长章切片的"章尾"被悄悄切掉

- **现象**：超长章按"首/中/尾"均匀采样，尾段（真正的章尾）始终丢。
- **真因**：三段预算 `833×3 = 2499` + 2 个省略分隔符（8 字）= **2507 > 2500** → `_assemble` 兜底 `text[:2500]` **从尾部切**，正好切掉尾段存在的全部意义。
- **修法**：预算先扣掉分隔符占用（`max_chars - 2*len(_SEP)` 再三分），段间 `"\n\n"` 也计入预算。
- **复发判据**：**凡是"拼接后裁剪"，先算清拼接符/分隔符占了多少。** 从尾部截断的兜底一定会优先牺牲你最后加进去的那一段。
- **证据**：`src/book2vido/segmenter.py` `_assemble/_fill_*`。

<a id="l-07"></a>
### L-07 · 改了算法，产物一点没变

- **现象**：修好了 L-06 的采样算法，重跑 `text.txt` 还是**旧的被截版本**——修复不生效。
- **真因**：章文本缓存的键含 `(书, 章, max_chars)`，但**不含采样算法本身**。
- **修法**：加 `segmenter.VERSION` 进键（`text_key = "seg2|chars2500"`），**改算法必须 +1**。
- **复发判据**：**任何"代码逻辑 → 产物"的缓存，键里必须有逻辑版本号。** 问一句：改了这段代码，键会变吗？
- **证据**：`src/book2vido/segmenter.py` `VERSION`；`cache.py` `text_key()`。

<a id="l-08"></a>
### L-08 · `--chapter 0` 静默走了"整本出片"

- **现象**：传 `--chapter 0` 不报错、退出码 0，用户拿到一条**完全不对**的片子，没有任何提示。
- **真因**：`want_chapters = bool(a.chapter or ...)`——**`bool(0)` 是 False**，于是被判成"没给章参数"，走了 T2V-001 老路径。
- **修法**：用 `is not None` 判"有没有传"，不用 `bool()`。
- **复发判据**：**代码里每出现一次 `if x:`，问一句"x 为 `0` / `""` / `[]` 时该走哪条路"。** 用户明确传了 0 和用户什么都没传，是两件事。
- **证据**：`src/book2vido/__main__.py` `_run_cmd()`。

<a id="l-09"></a>
### L-09 · 文档说"MD 走正则分章"，实际永远整本

- **现象**：非 PDF（MD / 长文）永远落到 `whole-doc`，与 `extractor` 文档所称"分章走 outline 的正则/整本分支"不符。
- **真因**：正则兜底被**关在 `if suffix == ".pdf"` 里面**——文档与实现互相打脸。
- **修法**：不是"把正则放开"就算修好（那样会更好笑，见下），而是**把限制写实**：非 PDF 没有页边界 → `extract_pages` 整篇当一页 → 所有章都落"第 1 页" → `_to_chapters` 推出 p1-p1 → **每章都切片到整篇，比粒度粗更糟**。所以非 PDF **一律 `whole-doc`**，并改掉误导性文档。
- **复发判据**：**文档里每条"支持 X"都要能找到一段真跑它的测试；找不到，就不是支持，是愿望。**
- **证据**：`src/book2vido/outline.py` `build()` 注释；`extractor.extract_pages()`。

<a id="l-10"></a>
### L-10 · 构建"每次成功"，产出的包用户装不上

- **现象**：`bash packaging/build_app.sh` 每次都绿、产出 115MB 的 `.app`；但把包给"没有任何技术背景的人"，他一拖书就卡住。
- **真因**：`FFMPEG_SRC` **默认是空值**，缺 ffmpeg 时只打 `warn`（"用户需自行安装"）。作者本机有 Homebrew 装好的 ffmpeg → **本地测试永远是绿的**；用户本机没有 → 弹「请在终端执行 brew install ffmpeg」。**静默降级 = 把失败从构建期推迟到用户期。**
- **修法**：加 `SHIPPABLE` 状态位 + `degrade()` 记录；构建报告打印「可分发性 ✅/❌」；**默认拒绝产出不可分发的包**（`--allow-unshippable` 才放行）。
- **复发判据**：**"作者本机能跑"和"能交出去"是两件事。** 凡是打包/分发链路，必须有一个**机器判定的"可分发性"结论**，不能靠人记得。
- **证据**：`packaging/build_app.sh` §可分发性 + §门禁。

<a id="l-11"></a>
### L-11 · 探针报"失败"，其实是探针自己不公平

- **现象**：验证 AC-7（首/中/尾采样）时，探针取原章 **0.95** 位置的字，报告"尾段丢失" → 差点当成缺陷改错地方。
- **真因**：0.95 位置恰好落在采样**间隙**里。尾段是从章尾往回取的 833 字，起点在约 0.9507 处——**探针取的位置不在任何采样窗内**。
- **修法**：改用"原章前 12 字 / 正中 12 字 / **末 12 字**"做探针，复测得 22/22 全过。
- **复发判据**：**探针给出"失败"时，先证明探针是对的，再下结论。** 假阳性比漏报更贵——它会让你去修一个没坏的东西。
- **证据**：`specs/2026091518-book2vido-chapter/verification-report.md` AC-7 条。

<a id="l-12"></a>
### L-12 · 对外 slogan 的数字，实测对不上

- **现象**：产品 slogan 定为「30 秒 666kb」。实测 4 条产物：时长 **29.3–38.9 s**、体积 **556–709 KB**——「666KB」在区间内，但**「30 秒」只有 1/4 达标**。
- **真因**：**对外宣称的数字也是一种"派生值"**——它由**当时某一次**产物决定，但产物后来变了，也没人会在改完代码后想起它。
- **修法**：数字型文案落成**区间**（「半分钟，不到 1MB」），并把每个数字回挂一条可复现的实测命令。
- **复发判据**：**发布前把所有对外数字列成一张表，逐个跑命令核。** 数字型文案被打脸，损耗的是整条内容的可信度。
- **证据**：`doc/11-产品化路线看板.html` §06。

<a id="l-13"></a>
### L-13 · 写了 `.gitignore`，却什么都没被忽略

- **现象**：给 `.gitignore` 加了 `cache/` 和 `.backups/`，`git add -A` 之后**165 个缓存文件 + 11 个备份文件全被暂存**了。
  `git check-ignore -v cache/...` 答"未被忽略"。
- **真因**：**注释写在了 pattern 同一行**——`cache/                    # 三层缓存：...`。
  gitignore 里 `#` **只在行首**才是注释，**行内注释不被支持**，于是 pattern 整个变成
  `cache/                    # 三层缓存：...`，永远匹配不上任何东西。**不报错、不提示、不警告。**
- **修法**：注释独立成行。
- **复发判据**：**凡是「声明式配置文件」（`.gitignore` / `.dockerignore` / `.npmignore` /
  `MANIFEST.in` / `.editorconfig`），改完必须用工具验一条真实路径**：
  `git check-ignore -v <真实路径>` 或 `git status` 复核暂存清单。
  **肉眼看着对 ≠ 生效。**
- **证据**：本仓 2026-09-15 首次 `git add -A` 的推送前复核输出（暂存 392 个 → 修正后重算）。
- **补充教训**：这个坑是在"推送前复核暂存内容"这一步抓到的，不是在写 `.gitignore` 时。
  **复核动作本身才是防线**——写的时候人一定会觉得自己写对了。

<a id="l-14"></a>
### L-14 · 文档写"11 个文件"，实测 13 个

- **现象**：`CHANGELOG.md` 与 `doc/12` 两处都写着「仓库里还有 **11** 个文件含 `/Users/<用户名>` 绝对路径」。
  2026-09-15 推送前复核实测：**13** 个；且另有 **8** 个文件字面含 CodeMax——**两处文档都没提这一项**。
- **真因**：**把"某一刻实测的瞬时值"当成永久事实写进文档**。数字没附口径命令，
  于是每新增一个文件就漂一点——没人重算，也没人知道该重算。
  更隐蔽的是**两处文档互相抄**：抄的是同一个旧数，于是"两处互相印证"，看起来反而更可信。
- **修法**：①写计数型数字时**同时写下口径命令与日期**，让任何人一行命令即可复算；
  ②同一事实**只在一处定义**（SSoT），别处只引用、不复制；③改动相关文件后重跑一次口径命令。
- **复发判据**：文档/看板里出现「**N 个文件 / N 行 / N 处 / N 条**」这类**可枚举计数**时，
  追问一句：**复算命令在哪？** 找不到，它就是下一个漂移点。
  **与 L-12 的区别**：L-12 漂的是**对外宣称**的数字（会被读者打脸），L-14 漂的是**对己自述**的数字
  ——没有人会替你发现，所以更安静、更久。
- **证据**：`CHANGELOG.md`（T2V-003 段）、`doc/12` §03；修正提交 `042f160`。
- **自我印证（好笑但真实）**：把这条教训写进本文件这个动作**本身，就把数字又改了一次**——
  因为「错题库这个文件」也在含绝对路径的清单里，于是 **13 → 14**、CodeMax **8 → 9**。
  **教训：计数型数字不是"要不要复核"的问题，而是"复核的时点离落笔有多远"的问题。**
  写作顺序上，**先把所有文本改完，最后一步才填数字**。
- **同型复发（第三次踩，2026-09-15 晚）**：追加**铁律八**后，立刻查出 **5 处条数同时过期** ——
  `AGENTS.md` 写「6 条硬约束」· `HANDOFF.md` 写「铁律 7 条」· `CONTRIBUTING.md` 写「两条铁律」
  · `doc/16` 标题写「七条铁律」· `doc/README` 写「七铁律↔代码映射」。
  **而上一轮（加铁律七时）我只是把这几个数字从 6 改成 7** —— 那是**修症状，不是治病因**，
  所以下一轮必然再犯。
- **治本修法与一条自我批评**：**条数类计数一律不写第二遍**，改成「完整清单见 `CONSTITUTION.md`」。
  注意本文件与 `doc/README` 在**错题库条数**上**早就**写了"此处不写死，避免多副本漂移"——

### L-15 · 注释写"供 prompt 注入使用"，实际**零调用点**

- **现象**：`src/book2vido/icons.py` 里 `CONCEPT_KEYS` 的注释写着
  「受控清单的稳定排序键（**供 prompt 注入**与 resolve 优先匹配使用）」。

  本地匹配走的是另一个 `_SORTED`（那是对 `KEYWORD_ICONS` 整体排序，与它无关）。
- **真因**：注释写的是**写代码那一刻的意图**，代码后来演进了（注入源换过），注释没人跟着改。
  与 L-09（文档↔实现）、L-04（假可改口子）同族，但**更隐蔽**：
  它连"文档"都算不上 —— 读者对代码注释的默认信任度**比文档更高**。

  ②改动某处代码时，顺手 grep 一遍**被改动的名字**，看注释里的声称还成不成立。
- **复发判据**：读到「**供 X 使用**」「**用于 Y**」这类**用途声明**时，问一句：**谁在用它？**
  一条命令就能回答（全文搜那个名字），成本 30 秒。
  **零调用点的公开名字 = 注释在说谎。**
- **证据**：`src/book2vido/icons.py`（T2V-007 修正注释）

### L-16 · 正文标记被"注释里提到的同名标记"截胡

- **现象**：新写的提示词加载器**第一跑**就把 699 字符的正文解析成了 **5 个字符**（两个反引号之间的内容）。
- **真因**：`parse()` 用**子串匹配**定位正文标记（`text.split(BEGIN, 1)`），
  而文件头说明里恰好写着「`` `<!-- @prompt:begin -->` 与 `<!-- @prompt:end -->` 之间是正文 ``」——
  第一个命中的是**注释里提到的那一处字面量**，"正文"于是成了说明文字里的一小段。
  这类缺陷的特征是：**不报错、不崩、退出码 0，只是安静地取错内容**。
- **修法**：结构性标记一律**整行精确匹配**
  （`(?m)^[ \t]*<!--[ \t]*@prompt:begin[ \t]*-->[ \t]*$`）。
  这样正文、注释里随便引用标记都不再歧义 —— **修的是这一类，不是这一处**。
- **复发判据**：任何用 `split` / `find` / `indexOf` 定位**结构性标记**的代码，问一句：
  **如果这个标记出现在正文里（被别人引用、被当示例），会怎样？**
  答"会取错" → 改成整行/唯一性匹配，或加断言（如"只允许出现一次"）。
- **补充（怎么被发现的）**：肉眼几乎不可能发现（5 字符 vs 699 字符——**不比对根本不会去看**）。
  它是被 `tests/verify_prompt.py` 的**逐字节 golden 比对**当场抓住的。
  这正是 T2V-007 坚持"**先固化基线、再动代码**"的价值：代价 2 分钟，抓住一个高隐蔽缺陷。
- **证据**：`src/book2vido/promptlib.py`（T2V-007）；`tests/verify_prompt.py` 抓到

### L-17 · 日志写「分镜：833 字」，数字其实是**输入切片字数**

- **现象**：boss 看到 `· 分镜：833 字`，判断「25 页的章节只有 833 字，太小了」，
  于是怀疑切片算错。实测该章（第 3 章，p68-92 = **25 页**）：
  **原始 10,201 字符 → 切片 2,498 字符 → 产出 12 句**。
  **833 从未出现在这条链路的任何一步。**
- **真因**：那行 print 写的是 `· 分镜：{len(text)} 字`，而 `len(text)` 是
  **送进模型的输入正文字数**；分镜本身的大小由 `len(doc.scenes)` 表示
  （缓存命中那行打的正是「12 句」）。
  **一个名词指了两件事** → 读的人只能猜到错的那一个。
  833 的真实身份是**三段采样的单段预算**（旧版 `max_chars // 3`；修正后 `(2500−8)//3 = 830`），
  `833 × 3 ≈ 2498` —— 它只出现在**旧缺陷记录**里，与"分镜"无关。
- **修法**：日志里的名词与变量语义**一一对应** —— 输入叫「正文切片」，产出才叫「分镜」。
  更好的做法是把两个数一起打出来（输入多少字 → 产出多少句），让读者不用猜。
- **复发判据**：**每个 print 里冒号左边的名词，问一句「这个词在代码里只指这一件事吗？」**
  同一个词在别处有另一含义 → 改名，或把两个含义都打出来。
  **变体（同批发现）**：标签对了但**数字口径**没写 —— 同一行的数字是"花费"还是"节省"？
  是"整机功耗"还是"增量功耗"？`demo/README` §5 的「成本 ≈ ¥0.0004/条」就属于这一类：
  它是**花的电费**，不是**省的钱**，且 30W / ¥0.6 都是**假设值**（口径已补进 `doc/01-llm-local.md`）。
- **附带**：该口径原指针「见 `doc/01-llm-local.md`」**指向空处**（该文件当时无任何成本章节）
  —— 与 L-09「文档↔实现」同型：**指针和内容分别演进**。凡写「见 X 的 §Y」，点一次看它真在不在。
- **证据**：`src/book2vido/pipeline.py`（`_produce` 的分镜分支）；`demo/README.md` §5；
  `doc/01-llm-local.md` §成本口径（2026-09-15 补）

### L-18 · 「同一件事」被 N 处各写一遍（路径推导 / 魔数常量）

- **现象（两个实例，同型）**：
  ①**「我的项目根在哪」被 6 处各写一遍** —— `__main__.py`（config 与 sys.path）·
  `binpaths.py`（vendor）· `cache.py`（cache 根）· `promptlib.py`（prompts）· `visualizer.py`（project_root），
  写法都是 `Path(__file__).resolve().parents[2]`。
  ②**电费公式被 3 处各写一遍** —— `0.03 * sec / 3600 * 0.6`（`pipeline.py` 两处 + `__main__.py` 一处）。
- **真因**：**每一处单看都是最省事的写法**（自己算一下就好，不用新开模块）。
  问题在于**没有任何一处是"权威定义"**，而且各处的**写法并不完全一致**——
  于是 `grep parents[2]` 能搜到，`grep 0.03` 搜不全 `0.6` 的组合。**"搜一遍"这个动作本身不可靠。**
- **危害不是"要改 6 处"，而是"改了不知道要改 6 处"**：
  移动一次模块（深度 +1），6 处推导同时指错层。其中 `cache` 与 `binpaths` 两处
  **不报错**——只是默默在别处建缓存、默默退回系统 PATH 找 ffmpeg。
  而**本机恰好有 Homebrew ffmpeg 和已有缓存，所以本地测试永远是绿的**（与 L-10 同构：错误被环境掩盖）。
  旁证：`packaging/build_app.sh` 顶部注释不得不写一句禁令
  ——「config.yaml / assets 依赖 `__file__` 回溯到 Resources/，**勿随意挪动**」。
  **当一条约束只能写成"别动它"时，说明它还没有被抽象好。**
- **修法**：**抽成唯一处**。①路径 → 一个 `project_root()`，各模块调它；
  ②公式 → 一个函数（顺带把 30W / ¥0.6 从魔数变成有名字的常量）。
  抽出之后，"移动模块"从**危险操作**变成**无害操作**。
- **复发判据**：看到 `__file__` / `parents[` / 裸的数字常量 / 重复的字符串路径时，问两句：
  **「这个值在别处还写过吗？」**「**我 grep 的那个词，能覆盖所有写法吗？**」
  补充判据：**当某段代码旁边出现"别动它 / 勿随意挪动"这类注释时，它就是待抽出的信号。**
- **证据**：`doc/17-结构诊断与重构方案.html` §S-1（6 处的逐条后果表）；`packaging/build_app.sh` 顶部注释
- **整改（2026-09-15 22:30，已关闭路径那半）**：路径推导收敛为 **`paths.project_root()` 一处**
  （`grep "def project_root"` → 1；真实 `parents[` 使用只剩 2 处，其中一处是 `sys.path` 的**另一种语义**，已加注释防误合并）。
  ⚠️ **电费公式那半仍未去重**（`0.03 * sec / 3600 * 0.6` 仍在 3 处，已登记为待办 ENG-5）——
  本节记的是**两条实例**，只关了一条。
  同时新增 **`tests/verify_deps.py`** 做机器守护：依赖方向是**唯一一条无任何测试覆盖**的契约，
  从此"移动模块"有可复跑断言，不再靠人记住 `build_app.sh` 顶部那句「勿随意挪动」。
- **同型变体：本机环境恰好掩盖缺陷。** 本例里 `cache` / `binpaths` 两处"不报错"的降级
  **不可能靠多跑几次发现** —— 本机有 brew ffmpeg、有历史缓存，测试永远绿。
  判据：**如果这个缺陷换台机器就暴露，那它不是"没问题"，是"没被环境踩到"。**
  这类只能靠**换环境或读代码**发现 —— 与 L-10（构建"成功"但包装不上）同构。

### L-19 · 共享数据寄居在其中一个消费者家里（跨层耦合）

- **现象**：`CONCEPTS`（「概念名 → 图标 id」的映射，约 50 行数据）定义在 `icons.py`（图标**资产**层），
  但它的消费者有两个：**分镜层**（要"有哪些合法概念"注入提示词）与**画面层**（要"这个概念画哪个图标"）。
  于是 `scriptwriter.py` 里出现了 `from . import icons`——**生成层为了拿一份词表，被迫依赖资产运维层**。
- **真因**：一个数据有多个消费者时，作者通常把它放在**"最先需要它"的那个模块**里。
  这在当时是合理的（少一个文件），但它把**依赖方向拉弯了**，
  并且让**领域契约的归属出错**：`models.py` 里 `Scene.concept` 的注释写着
  「**须落在 `icons.CONCEPTS` 受控清单内**」—— 一个核心数据结构的值域约束，
  指向的是另一个模块的**内部常量**。读代码的人想弄清"concept 合法值有哪些"，
  得从数据契约一路跳到图标模块。
- **修法**：把 `CONCEPTS` **提升为独立的领域资产**（与 `models.py` 同层），两个消费者都向下依赖它。
  依赖图从「`scriptwriter` → `icons`」这条**弯**，拉直成两条平行的**直**线。
  **收益可检验**：整改后 `grep "from . import icons"` 应只剩画面层一处。
- **复发判据**：看到 `from .A import X` 而 **X 是一份数据（不是函数 / 类）** 时，问一句：
  **「这份数据的消费者只有 A 吗？」** 只要答案不是"只有一个"，它就不该住在 A 里。
  同型追问：**领域契约（值域 / 枚举 / 单位）是不是指向了另一个模块的内部常量？**
- **整改（2026-09-15 22:30，已关闭）**：`CONCEPTS` / `CONCEPT_KEYS` 提升为 **`concepts.py`**
  （与 `models.py` 同层，只依赖标准库 → 谁都能依赖它、不成环）；`scriptwriter` 改为
  `from .concepts import CONCEPTS`；`models.Scene.concept` 的值域注释同步改指 `concepts`；
  `icons` 保留 `KEYWORD_ICONS.update(CONCEPTS)` 的**同义词覆盖语义**。
  **本节事前写下的判据已兑现**：`verify_deps.py` 输出
  「依赖 icons 的模块：**['visualizer']**」—— 与上面那句"整改后应只剩画面层一处"完全一致。
  *（教训：**先把判据写下来，整改才有"完成"的定义**。否则只是"感觉清爽了"。）*
- **附带的教训：搬家不带着注释走，注释就成了谎。** 搬迁时发现 3 处注释仍写着
  `icons.CONCEPTS`、1 处写着"（见上）" —— 锚点已随搬迁失效。
  **改数据的位置时，要连"指向它的注释"一起改**（同 L-15：注释也要跟代码一起维护）。

### L-20 · 引用了不存在的样式类，浏览器一声不吭（交付物的"软引用"）

- **现象**：`specs/.../backlog看板.html` 里给已关闭的条目写了 `class="closed"`，
  但 `<style>` 里**从来没有 `.closed{}` 这条规则**。后果不是报错，是
  **那批条目被渲染成完全无样式**——"已关闭 vs 待处理"的视觉区分**整体消失**，
  而页面照常打开、照常能读，**看起来只是"设计得有点朴素"**。
- **真因**：**CSS 类名是软引用**。引一个不存在的类，HTML 规范合法、浏览器不警告、
  开发者工具不报红 —— 它和"调用未定义的函数"（`NameError`）是**两种完全不同的失败模式**。
  我们最擅长抓的是后者（会炸），这条属于**不炸的那一类**，而且伪装成审美问题。
  与 [L-13](#l-13)（写了 `.gitignore` 却什么都没被忽略）、[L-15](#l-15)（注释声明"供 X 使用"但零调用点）
  是**同一族**：**声明式的东西，没有任何人替你验证它是否被接上。**
- **修法**：交付 HTML 前用工具做一次集合差集 ——
  ```
  引用集合 = 正文里所有 class="..." 拆词
  定义集合 = <style> 里所有 .xxx
  差集①  引用 - 定义  → 静默无样式（真缺陷，必改）
  差集②  定义 - 引用  → 死样式（冗余，从模板抄来的残留；克制度量）
  ```
  本项目 2026-09-15 写 `doc/20` 时实跑：差集① 为空、差集② 命中 5 条（`pill` 系列 + `ul.plain`），
  已按克制原则删除（体积 21.1 KB → 20.5 KB）。
- **复发判据**：**凡是"写了名字但靠别处去解析"的东西，都要用工具问一次"它接上了吗"。**
  交付 HTML / 看板 / 报告后，跑一次差集；顺带看一眼**定义了却没人用**的样式 ——
  那是"从上一个模板抄下来没清干净"的证据，与 L-18（同一件事 N 处写）是同一枚硬币的两面。
- **同族追问**：`<a href>` 指向的文件真的存在吗？`<img src>` 的图真的在吗？
  它们和 CSS 类一样，**是软引用，不会报错，只会静静地什么都不做。**

### L-21 · 用管道测退出码，测到的是管道末端那条命令的码

- **现象**：验证「下限闸门」时写
  `cmd 2>&1 | tail -12; echo "退出码：${PIPESTATUS[0]:-$?}"`，
  打出来是 **0**（正确应是 1）。差一点据此判定「退出码没生效」，去改一段**本来是对的**代码。
- **真因**：两层叠加，**第二层是关键** ——
  1. `cmd | tail` 里 `$?` 是 **`tail`** 的退出码，不是 `cmd` 的。这是通用坑。
  2. 本机默认 shell 是 **zsh**，数组是 **`pipestatus`（小写）**；写 `PIPESTATUS[0]` 取到空值。
  3. 而 `${PIPESTATUS[0]:-$?}` 这个**兜底语法把"测不到"伪装成了"测到了"** ——
     空值时静默回退到 `$?`（= `tail` 的 0），于是打出一个**格式完全正常、看起来可信**的错数字。
- **真因（方法论层）**：这是 L-11「探针自己是对的才对」的**方向相反**的版本 ——
  L-11 是探针把**好的**报成坏的；这条是**测量失败却给出一个体面的数字**。
  共同点是：**验证动作本身没被验证。** 而这一族里，**"静默给出默认值"比"报错"危险得多**：
  报错会让人去查，默认值会被直接采信并写进结论。
  与 [L-08](#l-08)（`if x:` 对 `0` 走错分支）、[L-13](#l-13)（`.gitignore` 不生效）同族：
  **失败无声，且结果看起来正常。**
- **修法**：
  - 测退出码**不要接管道**：`cmd > out.log 2>&1; rc=$?` 再 `tail out.log`。
  - 真要接管道：**按 shell 选对写法**（zsh `$pipestatus[1]`，bash `$PIPESTATUS[0]`），
    且**不要用 `:-` 兜底** —— 测不到就让它显示为空/报错，别给一个像样的默认值。
  - 更稳的做法：让**被测程序自己**在输出里写结论（本项目的做法是 `verify_*.py` 以退出码 +
    `✅/🔴` 汇总行双通道自报），人只看程序说的话，不靠 shell 转述。
- **复发判据**：
  - [ ] **我这个数字是"程序说的"还是"我从管道里捞的"？** —— 后者要重测。
  - [ ] **`${X:-默认值}` / `get(a, b)` / `or 默认` 这类兜底，会不会把"没测到"变成"看起来测到了"？**
  - [ ] **数值"大幅好转"或"明显不对"时，先验工具再验代码。**（两个方向都要验，不只是好转。）

### L-22 · 守护脚本断言的是「环境状态」，不是「这次行为」

- **现象**：`tests/verify_cache.py` 第 ⑦ 条断言
  `assert not proj_cache.exists(), "验证不应在项目根留下 cache/"` ——
  在开发机上**永远为红**。迁目录时才发现它一直是坏的（此前没人跑，因为它在 `tools/` 里和探针混住）。
- **真因**：断言写成了**环境态**（"项目根不该有 `cache/` 目录"），
  而它真正想守的是**行为变化**（"**本次运行**没往项目根 `cache/` 里写东西"）。
  但开发态只要跑过一次出片，项目根本来就有一个（已 gitignore 的）`cache/` ——
  于是**环境一旦不是全新的，这条断言就必红**。
  它与 [L-13](#l-13)（写了 `.gitignore` 却什么都没忽略）、[L-15](#l-15)（注释的用途声明过期）
  是同一族：**声明了一个自己没验证过的前提。**
  与 [L-21](#l-21) 也同族：都是"验证动作本身没被验证" —— L-21 是测不到还给默认值，
  这条是**前提从来不成立却一直没人发现**。
- **修法**：把"环境该是什么样"改写成"**跑之前 vs 跑之后，差异是什么**"：

  ```python
  proj_cache = Path(__file__).resolve().parents[1] / "cache"
  before = sorted(p.name for p in proj_cache.iterdir()) if proj_cache.exists() else None
  ...                                   # 中间跑全部用例
  after  = sorted(p.name for p in proj_cache.iterdir()) if proj_cache.exists() else None
  assert after == before, f"验证不应改动项目根 cache/（前 {before} → 后 {after}）"
  ```

  通用形态：**快照 → 动作 → 比对**。凡是"应该没变"的东西，都别断言它的绝对值，
  断言**本次执行前后的差值**。
- **复发判据**：
  - [ ] **这条断言在"别人机器上 / 跑过一次之后"还成立吗？** —— 断言里出现
    `not exists()` / `== 0` / `is None` 这类**绝对态**时，先问"谁保证这个前提"。
  - [ ] **它守的是"环境干净"还是"我没弄脏"？** —— 只有后者是该守的；前者是别人的事。
  - [ ] **守护脚本自己上次跑绿是什么时候？** —— 长期没人跑的守护脚本，
    默认当成**坏的**（本次迁移 8 条里就有 1 条是坏的）。

### L-23 · 外部二进制在非交互 shell 里不存在（`command not found` ≠ 没装）

- **现象**（2026-09-19 实测）：在 Agent 的非交互 shell 里跑 `which ollama ffmpeg rsvg-convert`，
  **三个全部 not found**；而 boss 自己的终端里三个都能用。
  于是 `-m book2vido run` 报 ffmpeg 退出码 **127**，一眼看去跟「这台机器没装 ffmpeg」毫无区别。
- **真因**：三者都装在 Homebrew 前缀（`/opt/homebrew/bin`）下，而该前缀**不进非登录非交互 shell 的 PATH**。
  `PATH` 取决于**进程是怎么被启动的**（登录 shell / Agent / cron / Finder 双击），
  不是这台机器装没装。
- **为什么这是复发而不是新问题**：`tools/start_webui.sh` 早在 2026-09-16 就把同一件事写进了注释——
  「Finder 双击 / 窄 PATH 下 `ollama` 不在 PATH 里 → 命令根本没执行」
  「本机环境把它兜住了，所以永远测不出来」。
  **当时在 shell 脚本里修好了（`resolve_bin` 逐级找），但没有推广开**：
  ① `src/book2vido/binpaths.py` 后来独立解决了一次（源码侧）；
  ② `tests/verify_env.py`（2026-09-19 新增）一开始**又自己写了一遍查找逻辑**，
  直到回看才发现 `binpaths.resolve()` 已经是这件事的唯一实现 —— 当场改回复用。
  **同一事实在三个地方各自浮现了三次**，前两次各修各的，第三次差点再写一个副本。
- **与既有条目的关系**：与 [L-10](#l-10)（"本机能跑"≠"能交出去"）、
  [L-18](#l-18)（同一件事写多遍）、[L-22](#l-22)（验证动作本身没被验证）同族 ——
  共同形态是：**项目的某一处已经知道这个坑，但知识没有到达另一处。**
- **修法**：
  1. **源码侧**：一律 `from book2vido.binpaths import resolve`，**不再写第二套查找**
     （四级：环境变量 → 随包 `vendor/` → 包管理器路径 → PATH）。
  2. **脚本/文档侧**：凡要调外部二进制的命令，显式 `export PATH="/opt/homebrew/bin:$PATH"` 或用绝对路径。
  3. **体检**：`python tests/verify_env.py` —— 复用 `binpaths`，从一架机器上一次性说清"解析到了哪、缺了怎么补"。
- **复发判据**：
  - [ ] **新写的脚本 / 文档命令，在"最窄 PATH"下验过一次吗？** —— 最窄 PATH 的复现办法：
    `env -i PATH=/usr/bin:/bin sh -c 'command -v ffmpeg'`（应当为**空**，用来模拟 Agent / cron 环境）。
  - [ ] **报错是 127 就说"没装"了吗？** —— 127 = 命令没找到，**原因可能是 PATH 也可能是真没装**，两者必须区分。
  - [ ] **又要写一个 `which` / `shutil.which` 了吗？** —— 先搜 `binpaths` 有没有现成的。
