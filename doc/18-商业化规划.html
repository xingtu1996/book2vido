book2vido · 商业化规划

日期 2026-09-15 ｜ 状态 规划层，待拍板 ｜ 与 doc/11 / doc/12 的关系： 那两份是决策留档（起源、三问、四选项），本文是规划层（商业化怎么做才专业）

这份规划里最重要的一句话，是它的第一结论：现在不该做商业化。 不是因为不该赚钱，而是因为缺的东西不是规划 —— 是反馈。 已发布内容 0 条，外部用户 0 人。在这个数字上写收入模型，无论写得多细，都是编的。

所以本文的形式被这个判断决定了：它不给收入预测，它给「每条收入轨道的触发条件」。 每一项都回答同一句话：哪个指标到位了，才轮到动它。

第一结论

在 n = 0 的时候，"怎么做商业化"是个假问题；真问题是"先让谁用起来"。

专业投资人在审早期项目时，问的第一句是「你有哪些真实用户数据」，不是「你的商业模式是什么」。 没有数据的商业计划书，本身就是不专业的标志 —— 它看起来最完整，实际最不可证伪。

因此本文所有条目都带触发条件而非日期。日期会在条件未达成时制造"该做点什么"的假压力； 而在 n=0 时启动产品化，等于给一个没人用的东西加功能。

01市场与定位：先定「卖给谁」，再谈「怎么收钱」

用户分层：三层里只有一层会付钱

层是谁他要什么你给什么付费意愿
L1 读者内容读者 / 观众「这本书到底讲了什么」视频（免费看）不付费 —— 但他是分发燃料
L2 使用者朋友 / 工程师 / 读书会「把我看不下去的书变成视频」安装包 / 引擎（免费）少量 —— 但他是唯一的反馈源
L3 付费者？ ← 这一格是空的？？目前未知
那个空着的格子，是这份规划里最诚实也最重要的一格。 L3 为空不是缺陷，是当前阶段的事实。所有"谁该付钱"的假设， 都必须等 L2 有人真用了之后才能验证 —— 而在此之前，任何自称知道 L3 是谁的判断都是猜想。

赛道坐标：卡在一个「头部不感兴趣」的位置

赛道代表 / 模式我们的位置
AI 视频生成云端 API，按量付费，拼画质不竞争（铁律二：不烧钱，主动放弃画质军备）
书本 → 视频同类开源项目（星数极低）同一卡位，竞品极弱 —— 这是机会，也是"没人验证过需求"的信号
AI 摘要 / 知识蒸馏云端订阅差异：本地 + ¥0 + 出的是视频不是文字
听书 / 速读 App订阅制差异：输出是观点提炼，不是朗读原文
市场规模的诚实说法（不吹 TAM）。 这是一个小众工具市场。「想快速看完一本书」的人很多，但 愿意为此装一个本地模型（首次 4.9 GB 下载）+ 等 40 秒出片的人少得多。 这是产品形态自带的天然天花板，必须承认 —— 它决定了这个产品很难做成大生意，但很容易做成好内容和好口碑。 而这个"天花板"本身，恰好指向了本文第 03 节的结论。

02价值主张与免费 / 付费的切割线

价值主张（一句话，数字已按实测校准）

半分钟上下，不到 1 MB，不要钱，有书有电脑就行。

口径说明：原 slogan 写「30 秒 666kb」，实测区间为 29.3–38.9 秒 / 556–709 KB（详见 doc/11 §06）。对外数字必须扛得住核 —— 被实测打脸损耗的是整条内容的可信度。

切割线该切在哪：这是商业化的核心工程问题

不该切在「能不能生成」。两个理由，都是本项目特有的：

  • 引擎若开源，任何人都能自己跑 → 把功能锁起来没有意义，锁的是自己的口碑。
  • 我们的边际成本 ≈ ¥0 → 禁止别人用不会省钱，只会少一个传播节点。

所以要切的是「省事」与「规模化」—— 这是真实存在的稀缺，而且别人抄不走（因为它不靠功能，靠交付）。

免费（引擎 / 自建）付费（省事 / 规模化）
自己装 Ollama、自己下 4.9 GB 模型打开就能用，不用懂任何技术
一条一条跑批量：100 本丢进去，睡一觉拿结果
命令行 / 拖拽图形界面 / 网页
出问题自己看日志有人帮你定位
只有 macOS 包全平台可用
这条线的设计原则（一句话）。 免费版不能是残废版 —— 它必须是完整能力 + 高门槛。 付费买的不是功能，是省掉的门槛。 这样即使有人白嫖引擎，他也在帮你传播"这东西真能用"这件事。

03收入轨道：六条，按「启动成本」排序

排序依据必须先说明：按启动成本而非预期收入排 —— 因为在 n=0 时， 「预期收入」全是编的，而「启动成本」是能算的。这张表是本文最核心的一页。

这张表真正要传达的一个洞察（请重点看这一条）。 R1–R4 全是「卖人」（卖内容、卖时间、卖信任）；R5–R6 才是「卖工具」。 而它们的前置条件是同一句话的两面： "卖人"的前置是内容与信任，"卖工具"的前置是引擎先成为独立资产。
→ 所以短期收入路径在内容侧，长期产品路径在开源侧，两者不冲突，但顺序不能颠倒。
关于 R6，必须说一句重话。 托管 SaaS 会引入持续的云端成本，直接违反铁律一（零公司资源）与铁律二（¥0）。 所以它不是"以后再说"，而是：除非根本底牌换掉，否则不做。 这不是保守 —— 一旦上了云端，"边际成本 ≈ 0"这个唯一的结构性优势就没了， 换来的是一个和一个正常 SaaS 拼价格的普通生意。

04定价策略：锚是 0，这既是优势也是难点

锚点：竞品价格构成我们的锚

参照物计价方式它给我们的锚
付费 TTS / 语音合成服务按字符量我们的锚是「0」
云端视频生成服务按生成秒数
AI 摘要 / 知识工具订阅按月
"锚是 0"是双刃的。 它是最好的获客武器，也是定价的难点： 免费的东西不能直接涨价卖。想让用户掏钱，必须提供一个与"引擎"不同的东西 —— 这就是第 02 节那条切割线存在的全部理由。

分层定价（若走到那一步，按此梯度）

层价格卖的是什么
免费¥0引擎 + 自己动手（B 站教程级门槛）
一次买断低（两位数）打包好的安装包 —— 买的是"不用动手"
订阅低 / 月托管 + 批量 + 持续更新（对应 R6，已标为不做）
冷启动期的定价原则（本节的核心专家意见）。 不要给工具定价。给工具定价需要"用户已经认可它的价值"，而 n=0 时这件事无法验证 —— 定低了折算自己，定高了没有成交，两种结果都拿不到有效信息。

冷启动期该定价的是你的时间（咨询 / 课程，即 R3/R4）。 因为那是确定的稀缺品，定价不需要用户群，只要有一个人认它就行。
→ 推论：R3 应该在 R1 之后最先启动，而不是等产品成熟。

05单位经济：现在无法计算，而这才是诚实的答案

指标状态说明
边际成本≈ ¥0本地推理 + 免费 TTS。这是结构性优势，可支撑价格战
毛利率接近 100%（若成交）边际成本≈0 → 账面上最漂亮的一格
已投入现金¥0只有磁盘、电费与时间（电费口径见 doc/01 §成本口径）
获客成本 CAC无法计算无渠道数据。唯一已知路径是内容，成本＝时间
用户生命周期价值 LTV无法计算无付费用户，无留存数据
专家判断：那张"毛利率接近 100%"的表，是一张残缺的表。 它看起来极美，但缺了分母（用户数）和获客（CAC）。 而且这里有一条不那么直觉的规律： 边际成本越低的产品，通常越难获客 —— 因为低成本意味着没有差异化定价空间， 也意味着"省钱"这个卖点对个人用户几乎不构成购买理由（他本来就不用花钱）。
→ 与护城河那一节的结论同源：低成本不是护城河，低成本 + 已获客才是。

06增长飞轮：两条，但只有一条现在能转

飞轮 A · 内容飞轮（现在就能启动）

项目本身 → 内容（书评视频 / 公众号长文 / 贴图）
        → 读者 → 其中一部分成为使用者
        → 反馈 → 产品变好 → 产出更好的内容 ⟳

启动成本 ¥0，且不依赖用户群 —— 这是当前唯一能自己转起来的轮子。

飞轮 B · 开源飞轮（要有用户才转）

引擎开源 → star → 使用者 → 贡献 / issue
        → 产品变好 → 更多 star ⟳
飞轮 B 有一个残酷的启动条件。 它需要"有用户"作为第一推动力。n=1 的项目开源，换来的通常是 无人问津 + 一份隐性维护承诺 —— 两个轮子的第一推动力不同，不能混着说。
两个飞轮的交汇点（这一条同时解释了另一个问题）。 飞轮 B 的启动条件是 「引擎已经是独立资产」 —— 既要结构上独立（能被单独切出来），也要许可上可分（能单独授权）。 这两件事恰好就是doc/12 §03 的许可决策 与 doc/17 的包结构问题。
→ 结论：「包结构」与「商业化」不是两件事，它们是同一个问题的两个面 —— 「引擎与产品怎么切开」。

07阶段路线图：用触发条件，不用日期

阶段目标进入条件退出判据（可验）
0 · 现在拿到真实反馈— ≥ 5 个真人使用 + ≥ 3 篇已发布内容
1 · 验证弄清「谁在用、用来干嘛」阶段 0 达成 ≥ 3 人主动重复使用（不是一次尝鲜）
2 · 首批收入启动 R1 / R2阶段 1 达成 首笔收入 —— 不计金额，只计"确有人付费"
3 · 产品化做"省事版"（承接 R5）阶段 2 达成 且 随包 ffmpeg 完成 有人为「省事」付费
4 · 规模化可选：企业 / 云阶段 3 达成 且 许可决策落地 —（R6 需先改底牌）
为什么阶段 3 的进入条件里有一条工程项（随包 ffmpeg）。 因为产品化的物理前提就是"包能给不懂技术的人用"。 在它完成之前，「把包给别人用」这件事不成立 —— 不是"体验差一点"， 是用户机器上会直接停住。所以商业规划与工程 backlog 在这一点上必须对齐， 不能各排各的期。

09这份规划的自我审查

可能的批评回应
"通篇没给一个收入预测，这算规划吗？" 算，而且这才是 n=0 阶段的正确形态。给不出预测的时候硬给，是把风险包装成确定性， 那对决策的伤害大于帮助。本文给的每一条触发条件都是可验的 —— 这是预测做不到的
"六条轨道是不是太多了？" 是，但这六条的作用不是"都要做"，而是划出边界：告诉未来的自己哪些现在不能碰（R6）、 哪些前置没到（R5）、哪条现在就能启动（R1）。列出不做的，和列出要做的同样重要
"是不是违反了克制（铁律七）？" 没有。本文零新依赖、零新资产、零代码变更 —— 它是一份判断，不是一件工具。 且它明确把 R6（引入云端成本）与 R5（引入许可复杂度）压在条件之后，是克制的执行
