DOC/23 · 研究级架构评审

把「书变视频」当成一个研究问题来解

以文献坐标校准技术架构 · 以实测基线定位效率杠杆 · 以认知科学重审初衷
成文 2026-09-16 · 全部数字为本机实测或公开来源，口径见 §8
一句话结论：我们 65% 的算力花在「生成文字」上，只把 0.7% 花在「让人看懂」上—— 而后者才是这个产品唯一的目的。这不是性能问题，是资源错配。 三条文献证据（认知科学冗余效应、T2V 能耗标度律、Paper2Video 评估方法论） 指向同一个结论：该搬的不是速度，是预算。

1初衷重定义：我们到底在解决谁的什么问题

「把书变成视频」是方案，不是问题。用方案当问题，会导致所有优化都盲目—— 因为没有一个可证伪的成功标准。先把问题说清楚。

1.1 场景化：三类真实用户，只有一个是我们的

人群行为特征我们的适配度
深度阅读者
年读 10 本+，占 13.5%		 45.9% 仍最偏好纸质书；要的是沉浸与系统性 不服务 视频对他们是降维，不是升维。他们会读书，不需要代餐
听书族
占 38.7%		 已在用音频代餐，场景是通勤/家务 部分 我们有配音，但没有听觉产品该有的时长设计（30 秒太短，撑不满通勤）
想读但读不完的人
占比最大，无直接统计		 「没时间 / 没习惯」是制约阅读的首要因素；日均手机 109.5 分钟 vs 纸质 24.7 分钟 主战场 他们不缺内容，缺的是低门槛的第一次接触

重定义后的初衷（可证伪版本）

不是「让人不用读书」——那是自我否定（读了还想读才对）。
而是：在一个人决定是否值得为一本书投入 8 小时之前，用 30 秒给他足够的判断依据。
成功标准：看完视频的人，能正确回答关于这本书核心主张的问题—— 且显著高于"只看封面目录"的对照组。

1.2 为什么现在做：卡在增速最陡的那条曲线上

第二十三次全国国民阅读调查（2026-04-20 发布，样本 54.5 万，覆盖 31 省，推及 13.8 亿人）里， 数字化阅读各形态的接触率变化：

形态20242025变化相对增速
电脑端网络在线阅读68.3%66.4%−1.9pp−2.8%
电子阅读器23.9%21.3%−2.6pp−10.9%
听书38.5%38.7%+0.2pp+0.5%
视频讲书5.7%6.3%+0.6pp+10.5%

视频讲书基数只有 6.3%，却是唯一两位数相对增长的形态；同期电子阅读器在两位数下跌。 我们不是在一个成熟市场里抢份额，是在一个刚抬头的曲线刚起步的位置。 这个判断决定了策略：冷启动期优先级是「被看见的次数」，不是单篇完读率。

2文献坐标：这个领域已经有人把路标插好了

四个方向，每条都给出它对我们具体意味着什么，而不只是"知道有这么个东西"。

A · 任务定义与评估（我们最缺的一环）

来源核心贡献对我们的含义
Paper2Video
NUS ShowLab · arXiv 2510.05096		 首个 paper→presentation video 基准：101 篇论文配对作者真人演讲视频/幻灯片。 提出四个指标，其中 PresentQuiz 用「看完视频能否答对题」衡量信息传达率。 PaperTalker 多智能体：slide / subtitle / cursor / talker 四个 builder， 并按幻灯片并行生成以压缩总时长。 最大缺口我们零评估指标。 PresentQuiz 可直接抄成迷你版——这是从"能出片"到"证明有用"的分水岭
mPresenter
ACL 2026 Findings · han-etal-2026-mpresenter		 多智能体（Planner/Reviewer/Coder/Interpreter）分解：规划 → 受众导向批评 → 布局感知生成 → 跨语言图解释。 建 mPreBench：40 篇论文 × 5 语言 × 1600 道专家题。 它的 Reviewer 环节（受众导向批评）是我们完全没有的： 我们生成完就出片，从没有"这一版够不够清楚"的判断环

B · 认知科学（直接约束画面层设计）

效应实证结论我们是否违反
冗余效应
Redundancy Effect		 画面上重复呈现口播已有的文字，学习表现显著更差。 （Pastore 2010，154 名大学生，冗余组在两个测验上均劣于非冗余组） 正在违反见 §4.1，画面卡上印的是口播原句全文
模态原则
Modality Principle		 图应配口语而非文字——让听觉与视觉通道各担一路， 避免注意力在两处文字间分裂（Mayer & Moreno；Tindall-Ford et al. 1997） 正在违反同上：文字同时进了耳朵和眼睛
双编码
Paivio / Mayer		 两条通道承载互补信息时记忆最强——注意是"互补"， 不是"同一内容的两次呈现" 未充分利用第二通道目前在复读，没提供增量信息
时间压缩
Time-compressed speech		 压缩 25% 学习无损；50% 是可懂度上限； 播放速度超过 2× 后理解显著下降（Educational Psychology Review 2024, 36:79） 可用TTS 语速上调 20–25% 是免费提速， 且 30 秒时长本身在安全区

C · 能耗标度律（我们的技术路线有了学术级辩护）

关键事实：视频扩散模型「规模不经济」

  • 批处理几乎不省能：batch size 1 / 2 / 4 生成视频，单条能耗差异 < 3.3%。 因为模型单条就已跑在 GPU 热设计功耗附近，没有空闲余量可填。
  • 加 GPU 不省能：GPU 数翻倍 → 时间减半但总功耗翻倍，加上通信开销甚至更差。
  • 量级：CogVideoX 5 秒视频 ≈ 3.4×10⁶ 焦耳（Hugging Face 实测，CodeCarbon 计量）， 约为高清出图的 700 倍；Sora 2.0 Pro 12 秒 1080p 估算 ≈ 1313 Wh。

来源：Lights, Camera, Carbon: Architectural Scaling Laws for Video Generation Energy Consumption （arXiv 2607.04553，六个开源模型 / 三种 GPU 配置，拟合 MAPE < 3%）

这意味着什么：对外我们一直把"不烧显卡"讲成成本妥协（因为穷所以省钱）。 文献给了更强的说法——扩散视频路线在规模化下没有边际成本递减， 而我们的程序化画面路线有（渲染 12 张卡 0.54 秒，多一条片就是多 0.54 秒）。 这不是"便宜的次品"，是唯一能规模化的架构。这个说法可以硬气地讲。

顺带修掉的一个静默陷阱

config.load() 默认不读项目根 config.yaml，而内置 DEFAULT 里 provider="rule"。CLI 因为显式传了路径所以正常；但任何库调用方不传路径就会静默跑规则切句， 没有任何告警——实测分镜耗时 0.02s 就是这个症状。 本次评审因此新建的剖析脚本已强制要求显式 --config。
建议：把 DEFAULT 的 provider 与 config.yaml 对齐，或在未显式指定时打一行提示。属低优先级的卫生问题。

4三个反直觉发现

发现 1画面层正在做一件被实证为有害的事

visualizer.card() 把 scene.text（口播原句全文）印在卡上， 同时这句又被 TTS 念出来。于是同一段文字同时进入耳朵和眼睛。

这同时撞上两个效应：冗余效应（重复呈现降低学习表现） 与模态原则（图应配口语，不应配文字）。认知科学的预测很明确： 这样做比只在画面放关键词更差。

为什么这个发现值钱：它不需要新模型、不需要钱、不需要算力—— 只改渲染逻辑。而且它是唯一直接提升"初衷达成度"的改动（其余都是提升速度）。 在 0.54 秒的渲染预算里，我们有充分的余地把画面从"复读机"改成"第二通道"。

发现 2资源错配：65% 花在生产文字，0.7% 花在让人看懂

把基线按"服务于哪个目标"重新归类：

目标环节合计占比
把长文压成短稿（手段）分镜 65.2% + 切片 0.0% + 抽页 8.6% + 目录 12.6%86.4%
让人看懂（目的）画面 0.7% + 配音 4.8% + 合成 8.1%13.6%

86% 的资源在"说什么"，14% 在"怎么说"。 但产品的价值主张全在"怎么说"——同样是 12 句话，讲得清和讲不清是两个产品。 "极致架构"的第一刀不该砍在加速上，该砍在重新分配预算上。

发现 3我们最该抄的不是架构，是评估

Paper2Video 与 mPresenter 的架构（多智能体、Beamer 渲染、说话人头像）我们都不能直接抄—— 它们假设有云端大模型和付费 API，与零成本铁律冲突。

但它们共同的、零成本就能抄的东西是： 用「看完能否答题」衡量信息传达率（PresentQuiz / mPreBench）。 我们现在一条评估指标都没有——9 条 demo 片只能说明"能出片"， 回答不了"看完的人到底懂了没有"。

没有评估，所有优化都是盲调：改了提示词，不知道更好还是更差； 换了画面，不知道更清楚还是更花哨。这是从"玩具"到"研究级"的分水岭。

5极致效率：杠杆排序（按实测 ROI）

#杠杆预期收益成本置信度
1 Prefix caching
提示词模板固定，仅 chunk 变		 每章省掉固定模板的重复 prefill。prefill 是 O(n)，我们模板 + concept 清单不短， 理论收益直接作用在占比 65% 的那一环 低 待实测
2 think 分档
主链路 true / 批量初筛 false		 同文本对照：think=true 94.8s vs false 16.9s（5.6×）。 现已支持 --fast，但没有按用途自动分档的策略 低 已实测
3 抽页 / 目录结果持久化 首跑 16.2s（21.2%），已有 outline 缓存； 进一步可把抽页结果也按书指纹落盘，换章重跑不再重抽 348 页 低 已实测
4 阶段流水线
借鉴 PaperTalker 的 slide-wise 并行		 当前：N 章 = N × (分镜 + 配音 + 合成)。 分镜受 Ollama 串行限制，但配音/渲染/合成是 IO/CPU 密集，可与下一章的分镜重叠。 理论把总时长从 Σ(全部) 压向 Σ(分镜) + 尾部 中 理论
5 TTS 语速 +20~25% 时间压缩 25% 内学习无损 → 成片更短（省合成时间 + 更符合短视频场景）， 且可能提升完播 极低 文献支撑
— Ollama 并发 本机实测：串行 2.2s vs 并发 2.1s，省 5%＝噪声 — 已证伪
— 换更快的画面渲染 0.54s 已是噪声级，再快也没有意义 — 无价值

6极致架构：三个提案（带取舍，不粉饰）

提案 A · 画面层从「复读」改为「第二通道」

  • 做什么：卡上不再印口播全文；保留关键词作为锚点， 其余画面预算给口播里没有的信息——结构关系、对比、进度、数据、图标语义。
  • 依据：冗余效应 + 模态原则 + 双编码（§2-B）。
  • 代价：画面信息密度上升，渲染逻辑复杂度上升； 「看画面就知道在讲什么」的冗余安全感会消失——对静音刷视频的用户是损失。
  • 怎么补：保留字幕轨（可选开关），静音场景靠字幕，有声场景靠听觉通道。
  • ROI 判断：最高零新增成本，直击初衷，且预算充裕（0.54s → 哪怕涨到 5s 也只占 6%）

提案 B · 内置迷你 PresentQuiz 评估

  • 做什么：出片时同步生成 3–5 道选择题（同一本地模型生成，成本可忽略）， 攒成一个小 benchmark；对照组 = 只看目录 vs 看视频。
  • 依据：Paper2Video 的 PresentQuiz / mPresenter 的 mPreBench（§2-A）。
  • 代价：要人工校对题目质量，否则评估本身不可信；初期只能覆盖少量章节。
  • ROI 判断：最高（并列） 没有它，A 和 C 的效果都无法证明。这是所有优化的前提设施，不是可选项

提案 C · 阶段流水线 + 提示词前缀复用

  • 做什么：①把分镜阶段与（配音/渲染/合成）阶段解耦成流水线； ②固定提示词模板走 prefix cache。
  • 依据：§2-D 与 §5 杠杆 1/4。
  • 代价：流水线会破坏当前"一章跑完再看下一章"的确定性输出顺序， 与"可复现"这条既有优势有张力；prefix cache 收益尚未实测，可能落空。
  • ROI 判断：中 收益明确但依赖实测；建议等 B 建起来再做，否则不知道提速是否牺牲了质量

7优先级建议

顺序动作理由
P0建迷你 PresentQuiz（提案 B）没有度量，后面所有改动都是盲调。先有尺子，再动刀
P1画面层去冗余（提案 A）零成本、直击初衷、有实证支撑，且 0.54s 的预算里有大量空间
P2think 分档策略化 + 抽页持久化低风险提速，收益已实测
P3流水线 / prefix cache（提案 C）收益待实测，且要在 P0 之后才能验证"提速是否伤质量"

需要拍板的两件事

① 静音场景要不要保？ 提案 A 会削弱"静音刷视频也能看懂"的能力。 如果目标场景包含静音（通勤、办公室），需要保留字幕轨——这会让画面重新变拥挤， 部分抵消收益。这是产品定位问题，不是技术问题。

② 评估要不要做成人能看的？ 迷你 PresentQuiz 可以先只做内部基准（不公开），也可以做成对外可讲的差异化卖点 （"我们每条片都自带理解度测试"）。后者更有传播力，但需要题库质量过硬。

8口径与诚实声明

  • 实测数字均由本次新建的 tools/profile_pipeline.py 在本机跑出 （348 页 PDF，强制关缓存）。样本仅 2 个章节，单次采样，未做多轮取均值， 绝对值会有波动，但量级与环节排序稳定。
  • think=true/false 的 5.6× 来自 47 字短输入对照， 长输入下思考 token 可能饱和，不可直接外推到 2155 字场景。
  • prefix caching 与投机解码的收益是理论推断， 本机未实测，标记"待验"。不要当成已兑现的收益。
  • 认知科学结论均来自实验室情境的多媒体学习研究， 迁移到 30 秒短视频场景需谨慎；但冗余效应与模态原则在不同研究中重复验证，方向可信。
  • 未解决：本文没有回答"画面该放什么"的具体设计—— 那需要提案 B 的评估结果来驱动，先有度量再谈设计。
