日期 2026-09-15 ｜ 样本《关键对话》348 页 PDF（本机实测，非估算）｜ 分工：doc/20 定「做哪个形态」， 本文回答「现在这套东西的输入输出规格到底是什么」，并修掉一个真缺陷

本文是一份规格盘点——把「丢一本书进去、出来什么」用真实数据摊开，让后面任何讨论都有共同的尺子。
盘点过程中撞到一个必须修的缺陷，附实证与判据。

盘点结论

「一章有多长」不是关键——关键是「一章有多短」。

长度上限早就设计好了：单集恒定 12 句、约 35 秒、12 张卡，无论那章是 14 页还是 40 页。 真正会出事的是下限——本书里「参考文献」只有 5 个字、「附录D」只有 22 个字， 系统照样给它们各出一条 32 秒的片，内容是 12 句同义反复。

实测证据在 §04。修复是 3 行代码 + 一条可解释的判据， 不引入任何新依赖，直接过铁律七。

02一本书的真实账

样本：《关键对话》348 页。所有数字可由 tools/ 下的探针复算。

22 个顶层条目 ≠ 22 章

目录树给出 22 条，但按性质拆开，只有 11 条是书的正文章。这个区分很重要—— 它决定「出一本书」到底要出多少集，以及哪些条目本来就不该出片。

类别条数 条目该不该出片
书前材料5 赞誉、第2版序、第1版序、译者序、前言 可出，但非卖点
正文章节11 第1章 … 第11章（含「第10章 案例分析」37 页） 核心，就是它
书后尾料6 后记、参考文献、附录 A/B/C/D 不该出（料不够，见 §04）

出全书 vs 出正文：两笔账

口径集数 总时长生成耗时 电费说明
整本 --all（改前）22 ≈ 12.8 分钟≈ 18–23 分钟≈ ¥0.006 含 5 条垃圾集（全靠编，见 §04）
整本 --all（改后）17 ≈ 9.9 分钟≈ 13–18 分钟≈ ¥0.005 自动拦住 5 条附录，无需人工排除
只出正文11 ≈ 6.4 分钟≈ 9–12 分钟≈ ¥0.003 这才是「一本书 = 一部短片集」的正解

和「不分章」的旧行为比

指标旧行为（截头 2500 字） 现在（分章 + 首中尾采样）倍数
输出1 条 / 25 秒22 条 / 12.8 分钟31×
全书信息覆盖1.8%（只有开头）28.0%15.6×
电费¥0.0003¥0.00620×
这三个倍数放一起才是重点 成本涨 20 倍，覆盖涨 15.6 倍，产出涨 31 倍 —— 极致的资源效率就长这样： 一份电费的钱，换来一整本书的短片集。这也正是「用 AI 红利替代人力、而不是省钱」的实证。

03一章有多长 → 出来多少

这是 boss 原话问的那句。答案是：输入的料差 2.8 倍，输出的片几乎一样长。

章页数原文 喂进模型覆盖率出片
第5章 保证安全4016,879 2,49814.8%12 句 / 38.9s
第7章 陈述观点3614,423 2,49817.3%12 句 / ~36s
第2章 掌握关键对话177,978 2,49831.3%12 句 / 35.7s
第11章 综合应用145,384 2,49846.4%12 句 / ~35s
译者序（短章）31,536 1,536100%12 句 / ~33s
参考文献（极短）15 5100%12 句 / 编出来
输出不随输入伸缩：40 页和 14 页都是 12 句 35 秒。
所以「一章多长」问错了方向 —— 该问的是「一章有多短」。

规律：章越长，进模型的比例越低

长章走「首/中/尾各 1/3 预算」采样 —— 这是 4K 上下文下的刻意妥协，不是 bug。 但它带来一个反直觉的后果：短章反而「信息完整」。

「赞誉」3 页 1,224 字 → 100% 进模型，出片是全文转述。
「第5章」40 页 16,879 字 → 14.8% 进模型，出片是从不到六分之一里提炼的 12 句。
两集在播放列表里长得一样长，但信息密度差 6.8 倍。

想提高覆盖率？doc/10 §6 已逐条过闸： 调大 max_chars ❌ / 多轮调用 ❌ / 换长上下文模型 △ —— 接受上限但让它可见 ✅。 而且真正提高覆盖率的正解不在这里，在 §06 的「指定兴趣点」。

04一个真缺陷：22 个字也能出片（已修）

本次盘点最该修的一件事：已实测复现 → 已修 → 已实测验证。证据在 doc/assets/audit/。

实测：把「附录D」（22 字）丢进去

$ book2vido run --input 关键对话.pdf --chapter 22 --out /tmp/probe_ch22.mp4 --no-cache

[1/1] 第 22 章「附录D 本书作者团队 其他畅销作品推荐」p348-p348
    · 正文切片：22 字（上限 2500） → 本地模型（think=True）…
    · 画面：渲染 12 张卡…
    · 配音：12 句并发（workers=12）…
    · 合成：FFmpeg concat…

口播句数  : 12          ← 22 个字，出了 12 句
耗时      : 62.4 s      成片 32.85s / 584KB
单条成本  : ≈ ¥0.00031
根因（已修）：只有「空」的守卫，没有「太短」的守卫 pipeline.py 里唯一的拦截是 if not text.strip(): 不静默出空片 —— 它挡得住「整章取不到文本」，但挡不住「章的文本只有 5 个字」。 5 个字非空，于是照常进模型；而「出 12 句」是硬约束，模型只能编。

为什么本机永远测不出来：跑测试用的是正经长文，不会有人拿「参考文献」去测。 只有跑整本书（--all）才会踩到 —— 而那时你看到的只是「有几集怪怪的」， 不会意识到是系统在编。

闸门定在哪：用判据，不用拍脑袋的数字

不能定个「少于 500 字不出」——那是拍脑袋的数字，违反错题库 L-14。 用一条能解释给别人听的判据：

一句话换一句话。原文能切出的句子数 ≥ 目标句数（12），才允许出片。

依据：max_sentences 已经是配置里的既有值，判据直接引用它，不新增魔数。 原文只有 1 句而要求出 12 句，缺口只能靠编 —— 这句话任何人都能听懂。

条目字数 句数稀释比判定
参考文献50∞拦
附录D 其他畅销作品推荐22112.0×拦
附录C 想让自己的人生变得更完美吗46112.0×拦
附录B VitalSmarts公司介绍48781.5×拦
附录A 作者介绍558111.1×拦（差 1 句）
后记 10 年应用作者手记2,498670.2×过
全部 11 个正文章2,49865–810.1–0.2×过
判据的验证：拦下 5 / 22 条，正文零误伤 拦的正好是参考文献 + 全部 4 个附录；11 个正文章、5 条书前材料、后记全部通过。 边界也干净：附录A（11 句）差 1 句被拦，第2版序（15 句）通过 —— 不是模糊地带。
副作用是好的：--all 从此不会再产出垃圾集，同时省下 5 × 62s ≈ 5 分钟无谓耗时。

已修：判据落成纯函数，接线到四个入口

判据本体是 segmenter.insufficient_reason(text, target) —— 纯函数，不认识章节 （依赖保持单向：配置 → 调用方 → 判据）。调用点在 pipeline._produce()， 位置刻意压在取料之后、进模型之前：分镜是全流程最贵的一段（~36s）， 拦晚一步就是白烧一次模型。

入口改动行为
run_book
（--all / --chapters）		 新增 skipped 列表，与 failed 分开；单条被跳过不阻塞其余章 逐条 ⊘ + 末尾汇总
_run_cmd 单章 一条都没出 → 退出码 1（调用方要能判断「没拿到东西」） ⊘ + 非 0
run 兼容入口
（T2V-001 语义）		 catch 住打人话，不甩 traceback；不违背 AC-14 —— 这是内容可行性判断，不是链路差异 ⊘ + 非 0
batch 批量目录 单条短料不拖垮整批：记一行、继续下一条 ⊘ + 继续
为什么必须把「跳过」和「失败」分开 跳过是我们主动的判断（料不够，不出比硬出好），失败是意外（TTS 挂了、磁盘满了）。 混在一个列表里，用户会以为工具坏了；而跳过必须仍然打印原因—— 「跳过」不等于「静默」（军规 progress_visibility）。

守护：判据本身也要能被证伪

新增 tools/verify_gate.py（纯标准库），两类检查： ①14 条边界断言——含两条实测回归锚点（22 字附录D / 5 字参考文献）； ②真实书截面——独立断言「正文章零误伤」，判据收紧过头会在这里红。 目标句数从 config.yaml 读，不写死：配置改了 12→8 而脚本还按 12 验， 那就是在验一个已经失效的口径（本项目抓过多次「改了不生效」，故前置堵死）。

一个刻意的设计取舍：半角点号 . 不算句末。
它在中文里大量充当小数点（3.14）、编号（1.）、缩写（Mr.）、URL —— 收进来会造出假句边界 → 句数高估 → 漏拦（该拦的静默放过）。
代价是纯英文书句数被低估（可能误拦）—— 这是刻意选的：误拦会打出「⊘ + 原因」用户立刻看见， 漏拦是静默编造，正是本判据要消灭的那类缺陷。

05另外两个会踩的错位

都不是缺陷，是「用户预期」和「系统实际」对不上。

错位一：--chapter N 的 N 不是书的章号

N 是目录树里的顶层序号。因为书前有 5 条材料，所以序号整体后移 5 位： 

--chapter 2   → 第2版序        （610 字，2 页）  ← 用户以为要出「第2章」
--chapter 7   → 第2章 掌握关键对话（7,978 字，17 页）← 真正的第2章在这里
--chapter 22  → 附录D 其他畅销作品推荐

实测：cache/.../ch07/script.json 里写着 chapter_index: 7, title: "第2章 掌握关键对话"。 序号与章号分离是设计（要能点播序/附录），但用户不会知道。

错位二：输出文件有两套命名

位置文件名能看出是同一集吗
缓存目录cache/…/ch07/ch07.mp4看不出
正式输出samples/chapters/第2章_掌握关键对话.mp4看不出

一个是序号、一个是标题，中间没有对照物。本书内测时两者都存在，靠人脑记「ch07 = 第2章」。 低频问题，但排查时很费时间 —— 记一笔，不急着改。

06用户指定兴趣点 → 定向出片

这是 boss 提的那句「用户感觉不懂的可以输入，然后针对他的输入生成他想重点了解的视频」。

结论：能力已经在，缺的只是一个入口

书里的 71 个小节每一个都有精确页码 —— 但它们现在不可点播。

目录树里，小节被刻意设成 index = 0（outline.py 原注释：「小节不参与点播， 只用于 list 展示」）。而 by_index(0) 返回 None —— 序号 0 取不到任何东西。 结果：看着有一堆精细的切入点，一个都点不动。

实测：手工造一个小节去切片，通了

小节在目录树里：  index=0  p67-67   「我们的目标」
doc.by_index(0)  →  None                                    ← 点不动 ✗

手工造 Chapter(99, "我们的目标", 67, 67) 再切片：
  → 401 字 ✓
  → 「在本书接下来的章节中，我们将一一探索人们用来营造对话环境的技巧…」

结论：slice_chapter 吃的是任意 Chapter（含页码区间），不是「必须来自目录树」。
      能力齐全，缺的只是把小节页码接出来的那根线。

而且：指定兴趣点比整章更「完整」

切法原文 覆盖率出来的片
整章「第5章」（40 页）16,879 14.8%盲采样，八成内容没进模型
小节「我们的目标」（1 页）401 100%全文进模型，说的是这件事的完整意思
反直觉但成立 「只看一段」得到的片，信息比「看整章」更完整。 因为 2500 字的预算在小节上是宽裕的（100% 进），在长章上是稀缺的（14.8% 进）。 这条同时是「覆盖率怎么提高」（§03 的问题）的真实答案 —— 不是把预算做大，是把颗粒度切小。

三种输入形态（按成本从低到高）

形态用户怎么给 系统怎么定位成本
①「我要第 3 章的『暂停对话后该怎么做』」 小节标题精确匹配 → 页码 极低。已有数据，加一个 --section 出口
②「我想了解 p133-150」 直接给页码区间 极低。slice_chapter 本来就吃区间
③「我想知道怎么让生气的人愿意说话」 自然语言 → 检索小节标题 中。要么关键词匹配（免费、粗糙），要么过一次本地模型（一次调用）

① 和 ② 可以立刻做，是接一条已有的线，过三道闸没问题。 ③ 才是「自然语言交互」，它需要一次检索/理解步骤 —— 但注意： 这一步不需要实时，因为是异步出片，用户可以等 60 秒。

07「实时调剧情」的直播形态：建议先不做

boss 提到的那个启发（观众输入实时改剧情）。它很动人，但要先算清差距在哪。

维度现在 直播式交互需要差距
响应延迟62.4s / 集≤ 2s / 次 约 30 倍。LLM 独占 36s，且探针 2 证明加并发也没用
内容形态概要（12 句提炼）叙事（角色 + 状态 + 连续剧情） 不是同一件事。我们做的是「读懂」，它要的是「追剧」
成本闸本地推理，¥0.0003/条 实时互动要压延迟 → 通常要换云端 撞铁律一（公司资源）+ 铁律七（费用）
真正的障碍不是速度，是「剧情」这个词 我们的产物是概要：没有角色、没有状态、没有前后因果。 「实时调剧情」需要的是叙事引擎（谁在第几步做了什么、状态怎么延续）—— 那是另一个项目，不是这条流水线加个开关。

而且它跟 §06 的关系是「包含」：boss 想要的效果（用户输入 → 出他关注的视频）， 异步版就已经实现了 90%。直播只是把交付时间从 60 秒压到 2 秒，内容不会因此变好。
推荐：先做「异步交互」，把「实时」押后，判据写死 ① 先落 §06 的形态 ①②（指定章节/小节 → 出片），这是真正的按需； ② 等它跑出真实使用数据，再问「有没有必要实时化」——大概率答案是没必要， 因为用户要的是「我要的那个视频」，不是「看着视频长出来」； ③ 重启条件：当本地模型首字延迟降到 < 1s 且我们有了叙事层， 这两条必须同时满足才动手。

08对外介绍（三个长度）

盘点顺带补齐的：这套东西怎么讲给别人听。冷启动期，「被看见」优先于「讲完整」。

一句话（推文 / 电梯）

把一本书丢进去，出来一集集能刷的短片 —— 全程本地跑，不花一分 API 钱。

一段话（GitHub about / 项目简介）

完全本地的「书 → 短片集」工具：PDF 进去，读出目录树，按章各出一条竖屏短片（12 句口播 / 约 35 秒 / 12 张卡）。 348 页的《关键对话》实测：整本 22 条 ≈ 13 分钟，电费约 ¥0.006。 信息覆盖 28%（旧式「截头 2500 字」只有 1.8%）。想深入某一段，指定它就单独出一条 —— 那一条的覆盖率是 100%。

一屏（公众号 / 详细介绍）

它解决的是一件很具体的事：字太多，读不完。

丢一本书进去，它读目录、按章切开、每章压成 12 句口播，配上图标卡和配音，生成一条竖屏短片。 一本书 = 一部可以按章刷的短片集。全程跑在你自己的电脑上：模型本地、配音免费、 画面用代码画 —— 没有 API 账单，断网也能出片。

两个诚实的地方：① 单章越长，进模型的比例越低（40 页的章只有 14.8% 的原文被读到）， 这是本地 4K 上下文的硬约束，我们选择把它写在明处而不是吹成无损； ② 料不够的章节（比如只有一行的「参考文献」）它不出片，而不是硬编 12 句给你。

想深入哪一段，就指定哪一段 —— 出来的那一条，反而是 100% 读过原文的。
